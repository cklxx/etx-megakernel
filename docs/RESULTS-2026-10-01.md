# Results, 2026-10-01: ETX reaches parity with vLLM at batch 1, and fusion finally pays

One machine, one protocol, one day. Qwen3-30B-A3B bf16, greedy, batch 1, 32 generated tokens checked against HF
greedy. Every number below was measured on **this** box and nothing is mixed across machines.

**Machine.** 1x AMD Instinct MI300X **VF** (SR-IOV virtual function), ROCm 7.14, 20 cores, 235 GB RAM. This is not
the Hot Aisle bare-metal box used on 2026-09-30, and its compiler is not the same: the megakernel builds to VGPR 128
with 15 spills here against 9 in the ROCm 7.2.4 container. **The 4.67 ms vLLM figure quoted before 2026-10-01 is from
that other machine and must not be compared with anything on this page.**

**Configuration.** Switch set B — `ETX_VL_XCD=1 ETX_VL_CHAIN=1 ETX_VL_DSL_GEMV=1 ETX_VL_DSL_TOPK=1
ETX_VL_DSL_ATTN=head ETX_VL_DSL_FOLD=1 ETX_VL_TOUCH=1 ETX_VL_COH=1 ETX_VL_FOLD_TOPK=0` at `ETX_VL_CU=256`, with
`ETX_VL_NT` on by default and the import prune in `build.sh`. 60362 tasks, 436 events, megakernel LDS 29736 B,
VGPR 128, 15 spills. Both gates pass: 32/32 tokens against HF greedy and `--check-dsl` clean at layer 47.

One run of each configuration per round, in the same order each time, so drift or thermal state cannot favour one.

**Verdict.** ETX is **0.040 ms (0.8%) behind vLLM's best configuration**, **0.068 ms (1.4%) ahead of vLLM with
AITER**, and **fusing the tiles beats launching them one at a time by 0.200 ms (3.9%)**. The first two differences
are small but real, not noise: ETX-fused's slowest run (4.913) and vLLM-default's fastest (4.855) do not overlap in
either direction with the other's range. The fusion result is unambiguous — the two distributions are 0.19 ms apart
with a combined spread under 0.03.

**On the spreads.** The ±0.003 quoted earlier in the day came from three back-to-back runs of one binary inside a
minute. Across a 15-minute interleaved sequence with two container launches between consecutive ETX runs, the real
figures are ETX fused ±0.014, ETX unfused ±0.003, vLLM default ±0.007, vLLM AITER ±0.019. ETX-fused also shows a
step rather than scatter — rounds 1–3 at 4.907–4.913, rounds 4–5 at 4.885–4.886 — which vLLM-default does not
mirror (4.855, 4.868, 4.867, 4.856, 4.869), so it is not box-wide drift. It is unexplained. It does not affect the
verdict: even ETX's best round (4.885) is above vLLM's worst (4.869).

## What moved the number, each measured on this box

| change | before | after | delta | what it is |
|---|---|---|---|---|
| `ETX_VL_COH` | 5.224 | 4.907 | **−0.317** | DSL tiles access activations coherently (sc0 sc1) and skip the per-task `buffer_inv sc1` acquire, which had been invalidating the XCD's whole L2 at every phase boundary |
| `ETX_VL_FOLD_TOPK=0` | 5.291 | 5.060 | **−0.231** | stop folding the MoE top-k into every expert task |
| `ETX_VL_NT` | 5.021–5.034 | 4.911–4.916 | **−0.106** | non-temporal weight loads, so weights read once per token stop evicting the MALL-resident KV cache |
| `ETX_VL_CU=256` | 5.327 | 5.260 | **−0.067** | 256 tasks per dense phase instead of 304 |
| import prune | 5.026 | 5.010–5.012 | **−0.015** | `build.sh` imported `wvsplitk` even when `ETX_VL_DSL_GEMV` replaced it, and its 32768 B declaration sized the LDS arena |

The COH row is a same-binary-generation A/B measured at the end of the day (`ETX_VL_COH=0`: 5.224/5.223/5.227,
three runs, 32/32 each; COH off also builds smaller — 11 spills against 15). The intermediate baselines shift
slightly between rows because each was measured against its own build generation; the rows are not a running sum.

**The top-k fold deserves its own note**, because it was our own optimisation and it was costing more than
everything we added that day. Under `ETX_VL_DSL_FOLD` all 448 expert tasks of a layer (192 `moe_up` + 256
`moe_down`) each recomputed the same 128-logit softmax and top-8 selection on wave 0 while the other fifteen waves
waited at the barrier. A timing-only ablation that fed fixed expert ids measured **0.676 ms/token**. Splitting the
folds — norms stay folded, top-k returns to one launch per layer — costs one phase and one hand-off and still nets
0.231 ms.

## Measured and rejected

Each was built and run; each number is against its own control on this box. All are off by default and the numbers
are recorded in-source so they are not retried blind.

| idea | result | why |
|---|---|---|
| `ETX_VL_ARGPF` — prefetch the next task's argument block during the arrive | −0.003 (neutral) | inside the spread; emission complexity for nothing |
| `ETX_VL_BAR2` — 3 barriers per task down to 2 | **+0.095** | after the fix that moved its global load off the publication path; it raises megakernel LDS 41448 → 61952, and one barrier is worth ~0.02 ms |
| 16 B split-tail so `moe_down` (K=768) leaves the 8 B load path | **+0.144** | per-load address tracking and a second per-row wave reduction cost more than the wider loads save; `moe_down` body 12.01 → 14.71 µs/layer |
| `ETX_VL_ATTN_WIDE` — attention block across 8 XCDs instead of 4 | +0.008 | the block is latency-bound, not parallelism-bound: `prep` moves 2.5 KB per task in a 5.9 µs body, 1.5% of one workgroup's streaming rate |
| batching `topk`'s coherent stores | +0.008 | its body is one write-through round trip that all stores sit behind, not 24 separable costs |
| dropping `topk`'s unused `tei` output | −0.004 | inside the spread; not worth diverging from vLLM's signature |
| skinny GEMM, dense phases only, B=2 | **+0.293** (7.104 batched vs 6.811 replicated) | the shared weight read buys 7%, because the second column doubles LDS reads and FMAs; and a batched phase must wait on every request's previous event, so it loses the slack replication provides |
| smaller workgroups for occupancy | not built | waves/SIMD = min(512/VGPR, LDS-limited); at 128 VGPRs the VGPR term is 4 regardless of workgroup size |
| fusing `prep` into `attn` | not built | `prep` is in-place and non-idempotent — it norms and ropes qkv rows back into themselves, so any shape with more than one task per kv head is *wrong*, not merely slow |
| sweeping `PART` for attention partitions | not built | `parts = ceil(MAXLEN/PART)`; 256 is the minimum correct value, 512 leaves tokens 768+ unattended, 128 only adds early-exiting tasks |
| `ETX_DEV_RESET` — the kernel rewrites its own per-step state so the host enqueues nothing | −0.008 wall (0.16%) | the host's 40.8 µs of enqueues do disappear (reset/step 57.8 → 17.0 µs) but 14 µs returns as device time — one workgroup copies the init images while the other 303 have exited — and the rest is absorbed by the wait; correct and available, not worth its machinery in the default build |

## Occupancy and cache, measured with rocprofv3

Counters filtered to `etx_megakernel_d0` — the run also issues 12,807 rocclr copy/fill dispatches that ruin any
unfiltered average. `rocprofv3` SIGSEGVs at teardown *after* writing its database, so the data is intact.

- **Occupancy is 4.000 of 8 waves/SIMD** (`MeanOccupancyPerActiveCU`, min = max across all 1055 dispatches), with
  98.6% of CUs occupied. Both resources bind at once: VGPR 512/128 = 4, LDS 65536/41448 = 1 workgroup. After the
  import prune LDS would allow 2 workgroups per CU, but VGPR still caps at 4. Reaching 6 waves/SIMD needs VGPR ≤ 85
  **and** LDS ≤ 21845 B; 8 needs ≤ 64 and ≤ 32768 B. `-DETX_MIN_WG_PER_CU=2` reaches the emitted
  `__launch_bounds__(1024, 2)` and the allocator still produces 128 VGPRs; `-mllvm -amdgpu-waves-per-eu` does not
  exist in ROCm 7.14's clang.
- **The fused kernel is not penalised here.** `etx_unfused_d0` is VGPR 104 → 512/104 = 4 waves/SIMD, the same. The
  hypothesis that a megakernel's max-over-all-tiles budget caps occupancy where separate launches would not is
  **refuted for this model**: both are register-capped at the same level.
- **85.9% of wave-cycles are `SQ_WAIT_ANY`** (303.8 M of 353.8 M) while `MemUnitStalled` = 0.0 and
  `LdsBankConflict` = 0.3. Waiting with the memory pipe never backing up means too little memory-level parallelism,
  not too little bandwidth — the same conclusion as the occupancy cap, from the other side.
- **L2 hit rate 31.9%** (`TCC_HIT` 23.84 M vs `TCC_MISS` 50.93 M), and 99.9% of misses become fabric reads at
  119.5 B per request for 6.08 GB — no read amplification. With `ETX_VL_NT` the hit rate rises to **34.6%** and DRAM
  read requests fall 3.9% (50.87 M → 48.91 M), worth the measured 0.106 ms.
- **Instruction cache 99.90%** (`SQC_ICACHE` 6,815,943 hits, 6,958 misses). The megakernel's switch over ~400 task
  types does not thrash it, contrary to the concern ForgeMegakernel raises in the literature. Ruled out.

## A third class of bug: the emitter and the compile disagreeing

Twice today a feature that changes device code was carried by a `-D` on the final `hipcc` while the emitter decided
independently, and the two disagreed with no diagnostic. `ETX_VL_NB` (skinny GEMM) would have had extra requests
read column 0. `ETX_DEV_RESET` was worse: `build.sh` appended the flag to an array and then **overwrote that array**
whenever `ETX_VL_COH` was also set —

```sh
COHF=(); [ "$ETX_DEV_RESET" = 1 ] && COHF+=(-DETX_DEV_RESET)
if [ "$ETX_VL_COH" = 1 ]; then COHF=(-DETX_DSL_COH); fi   # drops it
```

— which is every build of the best configuration. The host believed in a reset tail that was never compiled, skipped
its own reset, and every step after the first became a no-op: all workers surplus, 0/32 tokens, no error. (The
earlier diagnosis that the define "reached the final hipcc but not the device-code compile" was wrong; it reached
neither.)

Fixed structurally, not instance by instance. A conditionally emitted feature the host must know about now lives in
`plan.graph.codegen` and is published by `emit_plan_header` as `ETX_EMIT_<FEATURE>` in `plan_data.h`; the host gates
on that, and its env var can only turn **off** what was emitted. The kernel and the host are compiled together and
both include that generated header, so disagreeing would require the emitter to contradict itself within one call —
which `tests/test_feature_manifest.py` pins for `argpf`, `bar2` and `dev_reset`, in both directions, through a
marker unique to each feature's emission. No `-D` is passed for any of them.

The same round corrected an unsound ordering argument in `etx_device_reset`: the exit counter and the per-task
arrives are relaxed atomics on different addresses, so the counter reaching `gridDim.x` does not order the arrives,
and a late arrive could decrement an event word the reset had already refreshed — a hang after an unbounded number
of correct steps. A release fence before the increment and an acquire fence after the full count close it.

## Two methodology errors caught today

**Traces were taken during the prompt, not decode.** `--max-steps 8` stops inside the teacher-forced prompt where
`seq_len ≤ 8`. vLLM's paged-attention kernel partitions by a hardcoded 256 tokens and returns immediately past the
sequence end (`vllm/csrc/rocm/attention.cu:362,366-369`), so 16 of 20 `attn` tasks looked trivial and the phase
looked 4.3× imbalanced. In decode all 20 bodies are 5.7–6.7 µs — a 1.17× spread — and `attn`'s body is 6.28 µs, not
1.91. **Timing was never affected** (`host.hip:512` records only steps at or after the prompt end), but three rounds
of per-phase analysis rested on it, including a "partition imbalance worth 0.17 ms" that does not exist.
Weight-streaming phases were verified unaffected across the two regimes (`qkv` 6.62 vs 6.66, `moe_up` 20.03 vs 20.03).

**`span − mean body` charged work imbalance to skew.** A phase ends when its last-finishing task ends, so
`span = (that task's start delay) + (that task's body)`; subtracting the *mean* body attributes the difference
between the critical and the average task to start-up spread. It inflated `router`'s apparent skew to 4.34 µs/layer
when its real start delay is 0.68 — 97 of its 256 tasks are empty at `CU=256`, which halves the mean. The corrected
split is in `docs/BUDGET-2026-10-01.md`.

## Where the remaining time goes

From the decode-trace budget (`docs/BUDGET-2026-10-01.md`), for the 5.056 ms build that preceded NT and the prune:

| | ms/token | owner |
|---|---|---|
| streaming weights at the achievable rate | 1.594 | hardware |
| start delay of the critical task | 0.414, of which 0.048 is ours | hardware — ETX's spread is at or below `hw_stream`'s own span-minus-median everywhere but `qkv` |
| `attn` fixed cost | 0.301 | the imported vLLM kernel; `attn` runs *above* the contiguous HBM rate because the 104 MB KV cache is MALL-resident |
| hand-off, 9 edges × 1.00 µs | 0.433 | ETX, near the event protocol's floor |
| `router` + `qkv` spread | 0.212 | ETX |
| **our own DSL tiles** | **1.47** | MoE bodies at 65% of achievable (0.532), `prep`+`reduce` dependent chains of 8.5 and 8.1 hops against 3–4 necessary (0.548), `topk` (0.391) |

ETX's orchestration is no longer the limiting factor: the hand-off is at the protocol floor, the start delay is below
the hardware's own dispatch jitter, and fusion wins by 0.200 ms. What remains is dominated by the quality of the DSL
tiles, which is a larger item than the entire 0.040 ms gap to vLLM.

## Batch

ETX replicates rather than batches: `ETX_VL_REQUESTS=N` instantiates N copies of the task graph (60362 / 120724 /
239912 tasks and 436 / 872 / 1552 events for N = 1/2/4), so every request streams its own copy of the weights, while
vLLM reads a weight tile once per B-column activation matrix. Measured on this box, ETX/vLLM per token is 1.08× at
B=1, 1.29× at B=2, 1.90× at B=4. Batch is currently ETX's worst regime. The skinny-GEMM experiment above shows why
batching the dense phases alone does not fix it: the shared weight read is only 7% of the dense body, and the join
costs more than it saves. Closing this needs the whole layer to batch, MoE included, and a matrix-instruction dot
product for B > 1 rather than more scalar FMAs.
