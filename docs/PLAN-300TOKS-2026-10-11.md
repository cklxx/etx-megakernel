## 2. Correct fusion across the attention boundary

The ledger's handoff and attention scope entries are historical classifications, not a correctness proof for a new fused shape (`docs/GAINS-LEDGER.md:19,25`). The rejected shape runs in-place norm+RoPE more than once per KV head; declaring prep pure would miscompile it (`model.py:306-321`). The prep-early experiment in round22 was correct but neutral; its request-rate diagnosis is separate from the repeated-prep obstacle (`results_2026-10-01/round22/FINDING.md:16-44`). Vector prep has **already** been implemented (`etx/ops/attnprep.py:35-59,103-105`), so that old vectorisation is not a new cut.

### The implementable protocol: one prep owner, early publication, last partition reduces

Keep the current head-affine parallel partitions. Assign an owner for each `(step, layer, kv_head)`, with exactly one prep execution. The owner performs the existing q/k norm and RoPE, preserves its bf16 rounding and writes the current KV row once. After **all owner waves' stores have drained**, publish a head-local, epoch-qualified `prep_ready`. Publish it **before** the owner executes its attention partition, not at the end of the whole task. The other partitions acquire that publication and run their unchanged imported attention calls in parallel. The owner also runs its own partition.

Each partition writes the original bf16/fp32 partial buffers, drains all producing waves and arrives at a per-head completion counter. The last arrival executes the original imported reduce for that head. Election changes the worker, not the reduce's partition order. It must acquire visibility for **all** producers' partials before reduction; last arrival alone does not make those data loads safe. Publish the normal reduced-output event only after all reduce waves finish. The existing o_proj consumers then proceed.

This directly joins prep to the attention call and attention to reduce in the task body; it requires a new adapter/runtime protocol for **mid-body signals**, not a generic `pure` prologue fold. Import-round barriers must finish uniformly before reuse of a slot or before reduction. Static queues must place every producer before any blocked successor; a resident producer cannot be queued behind a waiting consumer on the same worker. A waiter must never monopolise the only execution resources its producer needs. Use discovered XCD identity, not block-index assumptions (`etx/machine/arch/gfx942.yaml:62,94,100`).

Norms surrounding this segment are part of the same audit: the input/residual norm is already folded into qkv, and the post-attention residual norm into router (`model.py:299-305`; `etx/ops/gemv.py:81-85`). Keep those folds and rounding points; do not book their removed launches again. The remaining imported input/final RMSNorm can be chained only with a consumer that fits the same ownership and visibility contract. A qkv or o_proj grid distributed across XCDs still needs its true fan-in/fan-out dependency. The isolated residual norm opportunity has **[U] zero separate credit**; it is not another attention boundary.

### Resources and the honest bound

The timed build uses **128 VGPR/lane, 44 B scratch/lane, 10 VGPR spills, 29,736 B LDS/block, four waves/SIMD [M]** (`results_vlbest2_2026-10-10/build_chkx.log:26-33`). Attention uses a **256-thread slot and 8192 B LDS**, reduce **eight 128-thread slots and 2176 B LDS/slot**, and RMSNorm **four 256-thread slots and 320 B/slot [M build declarations]** (`build_chkx.log:8-10`). Reuse their LDS lifetimes sequentially: reduce needs `8 × 2176 = 17,408 B [E]`, not an extra arena on top of attention. Prep declares no LDS (`attnprep.py:18-23`). Keep original partials in global storage for byte checking.

Estimated extra live owner/counter/epoch/address state is **4 to 8 VGPR/lane [E design allowance]**, not a compiler result. Adding eight would give `128 + 8 = 136`, whose register-only capacity is `floor(512 / 136) = 3 waves/SIMD [E]`, versus the existing four. That could make a 16-wave block unresident or spill more; the implementation must end prep's live ranges before attention and pass actual compiler/residency checks, with **no increase beyond 128 VGPR** as the CPU gate. An epoch/counter broadcast slot adds `4 × 4 = 16 B [E design]` LDS; external per-head state should not extend matrix temporaries' lifetimes. LDS target is `29,736 + 16 = 29,752 B [E]`, subject to actual arena allocation. More occupancy is not the premise.

The tempting alternative, one block owning all partitions and passing everything through LDS, has a resource problem. The current grid has **five partitions/head [M]** (`docs/FLOORS-2026-10-08.md:368`): `5 × 256 = 1280 threads [E]` exceeds the current **1024-thread block** (`model.py:80`); five attention slots use `5 × 8192 = 40,960 B [E]` before runtime storage. Serialising the fifth partition adds another attention round. A head's Q/K/V staging would add `(8 + 2) × 128 × 2 = 2560 B [E]` using the documented GQA/head dimensions (`docs/FLOORS-2026-10-08.md:44`; `attnprep.py:7,43-53`). No speed credit for this design until its parallelism and resources are measured.

Only two existing transitions, prep→attention and attention→reduce, are in this row. Using the historical **1.00 us/edge [M]** gives gross `2 × 48 × 1.00 / 1000 = 0.096 ms [E]` (`docs/BUDGET-2026-10-01.md:161`). **Net gain is [U]**: early prep publication and completion visibility still cost something. The ledger grants only a conditional `0 to 0.096 ms [E]` envelope, with zero guaranteed. Removing outer scheduler/broadcast/exit work can save time; the memory ordering itself remains. Argument loads classified inside a tile body remain in that body's row; if fusion removes them, reassign that saving rather than count it twice. Do not count the whole attention/reduce body allowance here. A current critical-path trace, not the number of idle CUs or all task waits summed together, decides the boundary budget.

Gate the protocol first with a small multi-partition payload test, byte-for-byte original imported calls, repeated cache-line reuse and epoch rollover. For a useful fusion result require at least `0.050 ms / 48 × 1000 = 1.042 us/layer [E threshold]` net improvement at unchanged bodies; otherwise close it as a route to this target. If it only relabels the waits, record that outcome and spend no time polishing it.

## 3. What the MoE skeleton really does

The in-tile ladder is deliberately wrong-output diagnostic evidence, **not legal model timing**. On its old build, no-weight-stream critical body was **11.55/18.37 = 62.9% up** and **7.64/11.11 = 68.8% down [E from M]**; roughly **6.5 us/task** remained unattributed (`etx/ops/gemv.py:17-29`). It disproves the idea that weight bandwidth alone owns the MoE time. It does not measure a removable 6.5 us slice of today's already-improved tiles.

The machinery is concrete:

1. Segment/range arithmetic and row transitions drive the unrolled load pipeline; each consumed vector advances the scalar row/segment counters, and a row transition flushes the accumulator (`gemv.py:177-184,201-258`). The load array and tail guards require waits/register lifetimes even when an ablation substitutes a constant weight vector.
2. Flush performs the deterministic wave reduction and deposits a partial in LDS (`gemv.py:205-214`). It is **not** an L2 write-back. WSUM already replaces part of this reduction; SCALAR already removes division/address work (`docs/TILES-2026-10-07.md:130-154`; `results_vlbest2_2026-10-10/build_chkx.log:2`).
3. Partials are zeroed, waves rendezvous, the epilogue sums in increasing wave order, then another barrier makes LDS reuse safe (`gemv.py:185-186,267-277`). GU1 already merges gate/up passes where each row belongs wholly to one wave; it removes the second pass's zeroing/reduction/barriers (`gemv.py:767-783`).
4. The bf16 output stores and publish must drain. DOMAIN release is a wait for outstanding stores; cross-XCD cached publication additionally needs write-back and a safe acquire (`etx/machine/arch/gfx942.yaml:24-46`; `etx/runtime/include/etx/primitives.h:35-69`). Coherent data can remove a redundant L2 write-back, **not** the store drain. `vmcnt` and `lgkmcnt` wait for the issuing wave's outstanding vector/scalar/LDS operations; barriers wait for participating waves. A source-level flush name is not proof of a fabric stall (`docs/FLOORS-2026-10-08.md:146-151`).

What might be removable now is **empty partial zeroing and cross-wave gathering for a row proved to have one contributing wave**, redundant loop guards for fixed shapes, and a duplicate barrier whose LDS lifetime/visibility proof permits removal. Specialise Qwen's proven GU1 row mapping, leave the wave sum and bf16 rounding identical, write gate/up row results directly to their existing LDS locations, then retain the barrier joining gate and up before SiLU. This may avoid gathering zeros from other waves. Down can straddle wave ownership and must keep its required partial order; it cannot inherit the up proof blindly (`gemv.py:183-184,272-275,768-775`). Do not omit real stores, skip the SiLU, reassociate fp32 sums, or replace payload visibility with a relaxed fence.

The current-shape price is only `0.139 up + 0.019 down = 0.158 ms [E]`, not `2 × 6.5 × 48 / 1000 = 0.624 ms [E invalid budget]` (`docs/PLAN-generic-decoder-2026-10-08.md:230`). A different tile mapping may change the achievable stream probe itself; that would require a new measured floor. The present plan cannot price that unknown as a second MoE gain.

### Deciding measurement: timestamps inside the correct tile

Instrument the **current correct tile**, with compile-time sampling of selected tasks/waves. Stamp: argument/routing completion, input staging completion, partial-zeroing completion, pipeline start/end, row-flush entry/exit, final wave join, cross-wave gather/epilogue completion, and output publication before/after drain. Separately stamp ETX's descriptor/wait/exit machinery; do not mix tile-loop and dispatcher costs. The existing timer is `s_memrealtime` (`etx/machine/arch/gfx942.yaml:93`); the hardware bench records its units (`bench/hw/hw_bench.hip:2`). Keep stamps in bounded state and write the trace after the measured region. Wave sampling does not establish the critical wave; correlate it with the actual last-completing task on the phase path.

Calibrate stamp overhead with an empty stamp pair and matched compiler resources. No extra fences in the main timing sample: a timestamp alone does not imply load/store retirement. If issue-versus-retirement needs forced waits, use a separately labelled probe with those added waits, not a performance number. Compare instrumented/uninstrumented correct builds; an instrumentation perturbation above **0.5 us per sampled critical body [E acceptance limit]** invalidates the attribution and triggers sparser stamps. Do not subtract mutually overlapping slices.

Pursue a specialisation only if the exclusive, correctness-removable part of up+down is at least `0.100 ms / 48 × 1000 = 2.083 us/layer [E threshold]`. Below that, close skeleton work for this target. On a pass, cap its gain by the current rebased body allowance and test a correct prototype; require at least **0.030 ms [existing KEEP bar]** in every faster interleaved pair (`docs/PLAN-generic-decoder-2026-10-08.md:154`). If instrumentation finds the retained store drain/reduction dominates, do not rerun ablations hoping to assign it elsewhere.

## 4. Reduce traffic without changing precision

Logical weight bytes are not automatically physical HBM traffic, and raising effective bandwidth is not itself reducing logical bytes. Preserve both counters in the next report.

- **Keep already-achieved cache reuse.** NT weights already protect the cached KV/activations; this measured **0.106 ms [M historical]** is in today's build (`build.sh:52-55`; `docs/BUDGET-2026-10-01.md:343-355`). KV read traffic is only **0.103711 GB [E logical ledger]**, and reduce **0.002421 GB [E]**, against MoE **2.415919 + 1.207960 GB [E]** (`docs/FLOORS-2026-10-08.md:100-106`). Even eliminating all KV reads from HBM would be `0.103711 / 3.93 = 0.02639 ms [E ideal-byte calculation]`, and much is already cached. Cutting those reads cannot fill the gap; attention is mostly fixed work, not streaming time (`docs/BUDGET-2026-10-01.md:255`).
- **One weight read, several consumers.** Dense columns reuse W only for different requests: batch one has one activation column. Gate and up use distinct weight rows, down distinct weights; GU1 merges their *machinery*, not identical bytes (`gemv.py:13-15,163-166,767-783`). The batch sharing variants were measured slower and violate this task's batch constraint (`gemv.py:44-71`). Cache actual duplicated metadata, norm/activation reads or shared Q/K inputs, but do not claim to divide the unique weight stream by a consumer count.
- **Exact cache retention across tokens.** Router weights are a small candidate: `48 × 128 × 2048 × 2 = 25,165,824 B [E]` from the model dimensions (`examples/llm/configs/qwen3-30b-a3b.json:1`). Ideal saved HBM time is only `25,165,824 / 3.93e12 × 1000 = 0.00640 ms [E]`. Keeping them cacheable may evict more useful data. Fleet's selective cacheability experiment lost badly, and its cliff was per-XCD L2 capacity (`fleet/docs/STATUS.md:80-81,228-233`). Full active weights cannot remain in a cache across a complete token; NT is already chosen for that reason (`gemv.py:124-126`). Routing prediction may prefetch, but cannot skip a new token's actual selected expert or reuse its prior activation.
- **Layout and mapping.** Interleave task rows / align bf16 vectors to improve transaction utilisation while retaining each dot's exact element order. The old **0.50 ms** mapping number is a model on build 3, not a measurement on the current build; large apparent rates were MALL artefacts, with HBM-resident points only **4–7% [M cited probe comparison]** (`docs/MODEL-vllm-kernels.md:568-582,646-649`). As a diagnostic scale, even applying that range to the entire `6.1904 / 3.93 = 1.575 ms` transfer floor gives `1.575 × (1 - 1/1.04) = 0.061` to `1.575 × (1 - 1/1.07) = 0.103 ms [E]`. Only exposed streaming could benefit; most of the MoE stream is hidden. **[U] zero additional credit**, because any actual gain must replace part of the dense/MoE rows below, not be added to them. Layout cannot improve a phase already at its applicable floor without a new floor/probe.
- **Streaming / overlap.** Greedy generation can keep token IDs on device (the current prologue/argmax already does); it cannot overlap causally dependent activation values (`examples/vllm_llm/host.hip:666-670`; `gemv.py:30-31`). A resident token loop would be new runtime/kernel work, with epoch/reset/abort proof, not a non-kernel setting. Treat any host saving inside the host row. Stage a next tile's exact bytes only when their address is known and resource headroom is proven. Fleet's across-wait prefetch was **4% slower**, split worker groups slower, and idle-worker prefetch gave no gain (`fleet/docs/STATUS.md:30,34,72,77-78`; `fleet/results/microbench_f_occupancy.txt:2-7`). ETX TOUCH is already present; LDS-direct on gfx942 is only a dword/lane and a BAR2 failure involved later descriptor loads, not an occupancy change (`docs/FLOORS-2026-10-08.md:309-319`). The old **0.22 ms [E]** first-row bound overlaps these same loads and boundaries. **Zero credit** unless the new current-path probe measures otherwise.

No KV truncation, windowing, dropped experts, lossy compression, approximate softmax or speculative token acceptance is allowed. Lossless encoding would need decode work and a measured net benefit; there is no evidence to price it. Prefix caching saves prefill, not the measured decode recurrence. More requests or GPUs change the target.
