# FC-2a routed excess and inactive pool baseline — 2026-10-24

## Verdict: (b), device tiles really re-read expert weights

The approximately 5x CPU count is **not** a 5x device payload traversal.
It combines real padded-row duplication with scalar FP8 scale lookup bytes.
Keep FC-2a failed; do not replace its distinct-weight bound with the larger
implementation count. `ledger --fc2a` now labels the routed failure with this
case (b) finding. No GPU measurements or latency claims were made.

### Source-level derivation

For a matrix R by C, block size B=128, the distinct FP8 storage bound is
`R*C + 4*ceil(R/B)*ceil(C/B)`. This includes scale storage once, whereas
reader observations count every scale lookup.

* `examples/glm53/native.h:74-82`: `glm_w(r,c)` requests one payload byte
  and a four-byte scale at `(r/B, c/B)` per FP8 element. Thus a scalar row
  costs `5*C` reader bytes; an interior scale is requested B squared times
  over its full block. `native.h:96-115` partitions rows among lanes and
  walks columns once; `native.h:162-166` invokes each projection once.
* `examples/glm53/phases.h:137-143,188-199`: CPU forces S=1 and takes
  the scalar fallback; the aligned device path selects vector loads.
  `phases.h:161-180` loads one 16-byte vector per (row, column chunk),
  with one four-byte scale lookup per vector. All S lanes partition chunks
  by `off=sl*16+n*S*16+iteration*NB*S*16`. No payload chunk is repeated
  within a row. A full scale block is looked up `B*B/16` times at source
  level. Compiler reuse and caches can reduce physical loads/transactions.
* `phases.h:576-588`: tile t owns pair indices
  `[floor((K+1)*R*t/T), floor((K+1)*R*(t+1)/T))`. It executes two pairs
  per unit. For an odd interval, `pr[1]` repeats the last pair's first row;
  the output guard discards the duplicate result **after** both dot products.
  Both gate and up payload rows are genuinely reloaded. `glm_each`
  (`phases.h:202-208`) partitions units across lane groups, so it does not
  eliminate this repetition.
* `phases.h:595-610`: down owns `[floor(H*t/T),floor(H*(t+1)/T))`;
  each selected expert's row is computed once, without pair padding.
* `examples/glm53/verify_moe.h:40-48,65-73`: verify partitions rows of
  one expert directly, no padding. Scalar `read` is outside the P-position
  loop. Payload multiplicity is one across the expert union, independent
  of P, but `glm_w` still looks up a scale per element on device as on CPU.
  Grouping positions therefore establishes payload reuse, not scale reuse.

`examples/spec/tile_reads.py` makes these formulas executable per task:
`rows` enumerates the row visits, `row_multiplicity` gives the load count
for every payload byte of each row, and payload/scale counts stay separate.
Device vector formulas require aligned compatible descriptors; unsupported
alignment falls back to scalar counts. These are source-level requests,
not disassembly counts or measured HBM traffic.

## Why index_kpool_compress_ape has no positive baseline

`examples/glm53/phases.h:383-393` computes `np=(pos+1)/POOL` and
`take=min(np,INDEX_TOPK/POOL)`. If take==np, it chooses all visible positions
and never enters any IAPE loop. At pos=0 module8 has np=0, so zero reads are
correct, not lost instrumentation. More generally zero persists until
`pos >= (floor(INDEX_TOPK/POOL)+1)*POOL-1`, which is 67 for module8.
When active, lane 0 requests each IAPE element three times per complete pool
per MLA tile: `3*np*POOL*ID` lookups per task. Native monolithic MLA also
has the three passes (`examples/glm53/native.h:237-243`).

A positive-baseline requirement cannot qualify this inactive tensor at position
0. The existing fail-closed diagnostic remains; it does not prove a device
failure or justify silently dropping the tensor. A future context-aware gate
must independently verify zero on the inactive branch and measure a positive
baseline at an active context, holding context constant across comparisons.

Status: OPEN; follow-up implementation belongs to the native tile owner.
Scope: remove odd-pair duplicate gate/up loads; investigate scale reuse in
vector decode and scalar verify without changing BF16 rounding or summation.
Do not tune unrelated kernels.

[estimate] At an assumed 4.3 TB/s, the example's 4,096 duplicate payload
bytes imply a 0.00095 microsecond bandwidth floor per projection. Including
all source scale lookup excess gives 136,064/4.3e12 seconds = 0.0316
microseconds. These are idealized streaming estimates, not additive measured
latencies; repeated scales/payload may hit cache or be compiler-reused.
No NVIDIA bandwidth assumption or end-to-end speedup is established here.

Before implementation: inspect generated device loads and a kernel trace,
measure padded versus unpadded row microbenchmarks and scale reuse, and record
the baseline time and gap ceiling. Go only if the saved loads produce a
repeatable positive latency change above measurement spread with identical
outputs. Otherwise retain the current tiles and close the package no-go.
GPU work requires a separately authorized budget and all repository gates.
