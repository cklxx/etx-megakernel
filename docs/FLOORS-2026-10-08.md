# Hardware floors of the Qwen3-30B-A3B decode phases, 2026-10-08

Date: 2026-10-08. Status: CPU estimate. No GPU measurement supports a new number in this file.
This file gives a hardware floor for each phase of one decode layer.
`python -m etx.tools.floors` reads the tables below. `tests/test_floors.py` checks the tool.
Section 2.2 of `docs/PLAN-generic-decoder-2026-10-08.md` uses the results.

## Rule

No phase floor comes from a measured task body. A body-derived floor makes the serial floor equal to the measured time.
Each phase gets one source tag:

1. `ISA hops x RTT`: count the exact dependent round trips of the phase in the ISA of the round11 build. Multiply each class by its price.
2. `probe`: use the hw_stream achievable time of the phase.
3. `probe + ISA hops x RTT`: add the ISA hops before the first weight-stream load and the store drain to the probe.
4. `bytes/BW`: only the byte floor applies.
5. `unknown`: no hop count and no probe exist. The phase adds only its bytes divided by the bandwidth.

The probe divides the bytes of one task by the hw_stream rate of one workgroup. The rate at 256 workgroups is an interpolation. Source: `docs/BUDGET-2026-10-01.md:86-90`.
The `hw_cohload.log` median of one workgroup is 0.28 us. The 0.50 us value is the span over all workgroups.

Each hop class has one price:
1. A coherent load (`sc1`) and the drain of a coherent store cost one coherent round trip.
2. A plain load costs the cached price. After an acquire (`buffer_inv sc1`), a plain load misses L2 and costs one coherent round trip. attn, reduce, in_norm and argmax start after an acquire.
3. A scalar load, a scratch reload and the drain of a plain store cost the cached price.
4. An LDS step costs nothing in the floor. The tables report it separately.

## Count rule

lucky and fix agreed on this rule. `etx/tools/isa_hops.py` implements it. `tests/test_isa_hops.py` checks each case with a small assembly text.

1. Count by data dependency, not by `s_waitcnt vmcnt(0)` alone.
2. Follow the result register of each load to the address or the control of the next load, or to the publish. A VGPR or an SGPR can carry it.
3. `lgkmcnt` waits a scalar load. `vmcnt(N)` waits a vector load. Each wait on the chain is one hop.
4. Loads in flight together count as one hop.
5. A scratch store and a scratch reload pair by base register and offset. A reload on the chain continues the chain and counts as one hop.
6. An LDS step (`ds_*`) is not a global hop. The table reports it separately.
7. A branch condition controls the loads up to the immediate post-dominator of its block.
8. A structured if/else writes a VGPR only in its active lanes. A read in the other lanes sees the old value. The tool tracks the lane sets with formulas of the branch conditions.
9. The publish is the last store drain, `ETX_RELEASE_DOMAIN`, at the end of the body.
10. A loop reports its hops for each extra trip. All layer phases run 1 trip of the chunk loop. in_norm runs 1 block for batch 1.

The tool has two lane models. `phi` lets an unclear read see both lane values. `kill` lets it see the last write only.
The floor uses the lower count. A floor must not exceed the true chain. In the matching build, the models differ only for moe_up. The table gives the lower count.

## Chains of the matching build

The ISA chains have these facts:
1. Every DSL phase starts with the same 1 scalar and 3 to 4 plain hops: the argument block, `nblk`, then the `dsl_args` fields. Source: `import.h:108`, `dsl_tiles.hip:229-232`.
2. qkv and router run the same fold body. The 8 row loads of the folded norm are independent. The ISA waits with `vmcnt(0)` in each row trip at line 108773. These waits are not on a data chain. Thus the fold adds 1 coherent hop.
3. prep: the head row and the position load are in flight together. The position feeds the cos and sin address. The store drain follows.
4. attn: 2 scalar and 5 plain hops after the acquire, then 1 scratch reload at line 108178, then the store drain. This is the only scratch reload on any chain.
5. reduce: the slot copies 2 and 3 give the longest chain. The pins on the slot register `v6 = tid >> 7` remove the copies that cannot run.
6. topk: wave 0 loads the logits with 1 coherent hop. The 8 selection rounds are LDS steps.
7. moe_up and moe_down: the expert id comes from the logits through LDS. Thus the weight address waits for 1 coherent hop.
8. o_proj: the ISA chain is 1.52 us at 0.50 us. The tag stays `probe`. See the o_proj note below.

The vLLM kernels compiled alone have a shorter chain. `MATCH/vllm_isa/orig_attention.s` gives attn 5 scalar and 2 global hops, and reduce 3 scalar and 1 global hop.
In the megakernel, the acquire before each imported task makes each plain load a miss. Thus the same loads cost a round trip each.

### o_proj note

The probe is 5.30 us. The probe plus the ISA store drain is 5.80 us. The measured critical body is 5.60 us.
The touch hook loads about 60 KB of the 65.5 KB weight slice of each task into L2 during the wait. Source: `ae1529c etx/ops/gemv.py:298`.
Thus the stream in the body is mostly L2 hits. The probe at width 256 also has an error of about 7%.
The tool keeps the tag `probe` for o_proj. It adds no hop. With this rule, no floor is above its body.

## Findings

1. The exact counts replace the ranges. The bandwidth floor sets the overlap floor in all four cases. The hop chain is 1.22 to 1.44 ms.
2. The gain without prefetch is 2.02 to 2.24 ms. The gain from prefetch is 1.10 to 1.59 ms. These two values are upper bounds. Thus shorter critical bodies stay the first lever. The measured evidence puts prefetch third. See "Lever order".
3. The five latency phases have 1.00 to 1.14 ms of body excess. Each latency body is 2.0 to 6.9 times its ISA chain.
4. qkv and router: the folded norm is 1 coherent hop in the data chain. The ISA serializes the 8 row loads with a `vmcnt(0)` wait in each trip. That serial order is a compiler lever, not a floor.
5. attn has the only scratch reload on a chain, 1 hop at line 108178. The spill costs 0.104 us per attn task in the floor.
6. The vLLM kernels pay a round trip for each plain load in the megakernel, because each imported task starts after an acquire. attn has 5 such loads. reduce has 5. in_norm has 7.
7. No phase floor is above its measured critical body. No tail floor is above its device time. o_proj keeps the tag `probe`. See the o_proj note.

## Lever order

The levers have this order. The values use 0.50 us and 4.3 TB/s.

1. Shorter bodies of the five latency phases: topk, router, prep, attn and reduce. The gain is at most 1.14 ms.
2. Shorter MoE bodies. The gain is at most 0.43 ms.
3. Prefetch across barriers. The theoretical gain is at most 1.40 ms. The realistic gain is much smaller. See the next section.
4. A shorter folded norm in qkv. The gain is at most 0.20 ms.
5. The start delay, 0.41 ms, and the handoffs, 0.43 ms. Both are near their floors.

The order changed on 2026-10-08. Before, prefetch was lever 2. The evidence below moved it after the MoE bodies.

### Realistic gain from prefetch

The value 1.40 ms is the serial floor minus the overlap floor. It assumes that all weight streams overlap all dependency chains. It is an upper bound, not an estimate of a real design.

Measured results do not support a large gain:

1. fleet measured idle-worker prefetch into the Infinity Cache (`--prefetch`). It gave no gain: 4.84 against 4.80 ms, and 4.77 against 4.70 ms with non-temporal loads. One CU streams about 30 GB/s. Thus the idle workers pull only about 60 MB per layer. The phases that can benefit are latency-bound, not byte-bound. Source: fleet-mi300x `docs/STATUS.md:72`.
2. fleet measured a prefetch of the first rows of the next task across the event wait (`--prefetch-next`). It was 4% slower: 3.812 to 3.815 against 3.673 to 3.682 ms. Each thread held 8 extra 16 B loads across the wait. The register cost was larger than the gain. Source: fleet-mi300x `docs/STATUS.md:30` and `docs/STATUS.md:78`.
3. fleet runs DeepSeek-Coder-V2-Lite with its own kernel. The two results are evidence for this model, not a measurement of it.

A prefetch of the first rows saves at most about 1 round trip per handoff. Each layer has 9 handoffs. Source: `docs/BUDGET-2026-10-01.md:161`, "handoff, 9 edges at 1.00 us", 0.433 ms in total. The upper bound is 9 x 48 x 0.5 us, about 0.22 ms. This is an estimate. No measurement supports it.

`b_r8base` already has this mechanism. The switch is `ETX_VL_TOUCH=1`. Source: `docs/BUDGET-2026-10-01.md:20` and `docs/MODEL-vllm-kernels.md` section 18. Wave 0 polls the event. At the same time, waves 1 to 15 read the first weight pass of the next task into the L2. Each workgroup reads 60 KB. TOUCH covers the dense GEMVs only: qkv, o_proj, router and lm_head. It does not cover the experts, because the expert rows depend on topk.
Section 19 of `docs/MODEL-vllm-kernels.md` measured the fold and TOUCH together. Build 3, with fold and TOUCH, took 5.895 ms. Build 2, without both, took 5.934 ms. The two switches together save only 0.04 ms. Thus most of the 0.22 ms is already in the measured 5.08 ms.

LDS-direct loads give a small extra gain at most:

1. On gfx942, the widest LDS-direct load is `global_load_lds_dword`. It writes 4 B per lane. The matching ISA has 0 such instructions. A new design needs new code generation.
2. `vmcnt` counts per wave. Thus the polling wave must not issue the prefetch. Other waves must issue it, as TOUCH does. Otherwise the `vmcnt(0)` wait of the polling wave also waits for the prefetch.
3. The shared tile arena uses 41,448 B of LDS. The next tile also uses the arena. Thus the prefetch area must be outside the arena. Each CU has 24,088 B of free LDS. This holds about 6 loads of 4 KB by all lanes of the workgroup.
4. TOUCH already puts the first pass in the L2. LDS-direct loads save only the step from an L2 hit to the LDS. This is less than 1 round trip per handoff.

The argument prefetch `ETX_VL_ARGPF` was measured as neutral, -0.003 ms. `ETX_VL_BAR2` was the build that was 0.095 ms slower. BAR2 raised the LDS of the megakernel from 41,448 B to 61,952 B. Source: `docs/RESULTS-2026-10-01.md:97-98`. Explain these two results before a new prefetch design.

## Limits

1. The counts come from one compiler, the one that matches the fingerprint. The 7.2.4 control shows how much a compiler change moves them.
2. The lane formulas are a superset of the true lanes. Where the two lane models differ, the floor uses the lower count.
3. LDS steps, barriers inside a task and the request rate of per-lane 2-byte coherent accesses are not in the floors.
4. The probes at width 256 are interpolations with an error of about 7%.
5. The handoff term is the measured 1.00 us per edge. It is not a hop count.
6. The trace is from 2026-10-01. The shipped build has bodies 2.80 us shorter per layer. Source: `docs/BUDGET-2026-10-01.md:104-115`.
