## Estimate method and limits

The per-file percentages below are editorial estimates of the ETX profile, with roughly ±10 percentage points of uncertainty.
They are not dictionary certification or a claim that that fraction of sentences passes every rule.
The overall editorial estimate is about 80–85%. `../deepseek/OPS-dsv2.md` remains below the target.
Its operation chains need a technical review before a safe full rewrite.

A separate mechanical screen checks sentence length above 25 words, semicolons, parentheses, and a narrow set of complex verb forms.
Each sentence gives four check opportunities. The score is the fraction without a detected issue.
The existing English files have 3,703 screened units and a combined score of 87.2%.
This is a limited diagnostic, not an ASD-STE100 compliance percentage.

The screen joins wrapped prose, separates table breaks, and substitutes one token for inline code, links, paths, and decimal values.
It excludes code fences, indented code, headings, Chinese lines, and very short fragments.
Some symbolic cells still trigger false positives. Some compound clauses and imperatives escape detection.
The 20-word instruction limit, voice, noun clusters, verbal `-ing`, paragraph topics, and terminology need human judgment.
Those rules informed the edits and conservative editorial estimates. Unverified dictionary entries do not count as confirmed passes.

The official Issue 9 sources and retrieval limitation appear in `STYLE-STE100.md`.
Technical nouns such as routing and scheduling remain where they name established concepts.

## Numeric contradictions: corrections supported by raw logs

### C1. Same-five-run wall gap

File: `../qwen/RESULTS-2026-10-01.md`, the wall-basis correction table and its headline.
Old: 0.242 ms and 5.0% behind vLLM. New: 0.237 ms and 4.9% behind.

Source: `results_2026-10-01/final/interleave.log`.
ETX fused wall values are 5.104, 5.104, 5.124, 5.104, and 5.103 ms/token.
The median is 5.104. vLLM default values are 4.855, 4.868, 4.867, 4.856, and 4.869, with median 4.867.
The gap is 5.104 − 4.867 = 0.237 ms. The relative gap is 0.237 / 4.867 = 4.87%, rounded to 4.9%.
Conditions: Qwen3-30B-A3B, batch 1, context 1024, same five interleaved rounds, wall basis.

The prior 0.242 used 4.862 from the separate ladder series.
`../qwen/VLLM-LADDER-2026-10-01.md` retains 0.242 and 5.0% because its denominator belongs to that series.

### C2. PhiMoE DSL output count

File: `GENERALITY-2026-10-02.md`, the round48 gate summary.
Old: 0 of 35k values. New: 0 of 31248 listed output values.

Source: `results_2026-10-01/round48/phi_full_gate1.log`, the five numerical output checks.
The count is 6144 + 4096 + 16 + 12800 + 8192 = 31248.
All five report zero values beyond 2 ulps. The final gate states 2 bf16 ulps at layer 31.
The count excludes the separately printed top-k ids. The new wording makes that scope explicit.
The correctness conclusion remains unchanged.

### C3. Bare-metal dependent-load denominator

File: `../qwen/VALIDATION-baremetal-2026-10-01.md`, the loaded dependent-chain comparison.
Old: 1107 ns against 103 ns. New: 1107 ns against 104.3 ns.

Source: `results_2026-10-01/baremetal/hw_all.log`, loaded vector L1/K$ rows.
The raw values are 1106.9 ns with `inv sc1` and 104.3 ns without it.
Their ratio is 10.6127, so the existing 10.6x remains correct.
The 103.3 ns value belongs to the VF series in `results_2026-10-01/round6/lat.log`.
That series gives 1174.8 / 103.3 = 11.3727, consistent with its retained 11.4x.

### C4. Cross-machine invalidate ratio

File: `OPTIMISATIONS.md`, the `ETX_VL_COH` row.
Old: 10.6× per hop “on both machines”. New: 10.6× on bare metal and 11.4× on the VF.
The raw loaded-chain rows in C3 support these separate ratios.
The qualitative conclusion remains: both machines show the invalidate penalty.

### C5. Machine independence of the invalidate penalty

File: `../qwen/VALIDATION-baremetal-2026-10-01.md`, the dependent-chain comparison.

Old: "Both numbers are machine-independent, so neither is an artefact of the virtualised box."

New: "Both effects hold across machines. Neither is an artefact of the virtualised box."

Reason: C3 and C4 give different ratios per machine, 10.6x on bare metal and 11.4x on the VF.
A ratio that changes with the machine is not machine-independent.
The narrower claim states what the logs support.
This wording change is a semantic change, not a style change.
It is registered here for that reason.

## Contradictions and claims without enough evidence for a numeric edit

### U1. README headline and fusion percentage

The displayed 4.823 / 4.998 pair implies a 3.5014% time reduction, not 1.2%.
This arithmetic does not prove that the numbers form a valid paired comparison.
`results_2026-10-01/round23/FINDING.md` records the older 4.937 / 4.998 comparison, consistent with 1.2%.
The raw archive search did not locate the newer paired wall logs.
Some 4.998 values occur in traced runs, which cannot substitute for an untraced wall pair.

README retains the headline values and 1.2%, but now assigns 1.2% to the recorded older comparison.
It explicitly marks the newer fusion percentage unverified.
It also distinguishes this DSL result from the all-imported claim.
Round24 records imported fused/unfused at 6.435 / 6.264 and qknr at 6.071 / 5.787.
These results do not support the previous unqualified statement that the production-kernel claim now holds.
No new measured win was invented.

### U2. Phase attribution subtotal

`../qwen/PHASES-2026-10-01.md`, Conclusion 1, lists +0.614, +0.355, and +0.500 ms/token.
Their arithmetic sum is 1.469, but the prose says “0.95 of the 1.50”.
The same section discusses the acquire contribution and overlapping build differences.
A valid correction needs a disjoint attribution ledger from the original phase traces.
The disputed sentence remains. Changing only 0.95 would risk double-counting and a different conclusion.

### U3. Bare-metal relative gap convention

`../qwen/VALIDATION-baremetal-2026-10-01.md` says 3.1% behind at 5.042 versus 4.887 ms/token.
Division by vLLM gives 3.17%, normally 3.2%. Division by ETX gives 3.07%, normally 3.1%.
The document later identifies a timer-basis mismatch in these historical comparisons.
The original percentage and later correction remain together. A new wall-basis comparison must use paired wall logs.

### U4. The 14x check-dsl moe_down reference

File: `GENERALITY-2026-10-02.md`, the round-48 section.
The text says the check-dsl fold branch had a `moe_down` reference that "differed by up to 14x while the device result was correct".
No file under `results_2026-10-01/` contains that ratio.

The statement dates from the round-48 session and predates this audit.

The text is left unchanged and flagged here.
