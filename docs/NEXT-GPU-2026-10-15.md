## GPU sequence and acceptance criteria

One MI300X, DeepSeek-Coder-V2-Lite-Base, bf16, context 1024, 32 greedy tokens, repeat 2. Pin every invocation to the
same GPU. Enable `ETX_DS_LAYER_METRICS=1`, retain 27 boundary lines per request, and record the reference hashes,
compiled arm identity, ROCm/compiler versions and GPU identity. Timings printed by these diagnostics have no
performance verdict.

1. Verify staged payloads and bindings; generate only missing certified references. A binding error is an input
   failure and stops model diagnosis. Preserve the rotation identities r0…r7 and token-window collision warnings.
2. Run x1km on r5 and r7 separately using `inplace_session layers <arm> --reference-dir <request-directory>`.
   Run the kept B1 arm on the same two references as a secondary recipe control. These are four model invocations.
3. Run `batch_session gate x8` on the certified eight-request set, twice in fresh result paths, to see whether the
   multi-request failure repeats. A failed diagnostic is expected evidence: retain its entire log and continue only
   to the remaining predeclared correctness diagnostics, never to timing rounds.

Each passing invocation must have 32/32 free-greedy and warm-up tokens, 27/27 consecutive hidden boundaries, no
host refusal, and all expected layer metrics. Each layer must keep the existing thresholds: relative max error
<=0.02 and cosine >=0.999. Missing/nonfinite metrics, absent tokens, wrong binary/input binding or incomplete output
are **INCOMPLETE**, not a pass. Tokens alone never waive a hidden-state failure. First-step layer checks do not
certify all hidden states on all 32 decode steps.

- If x1km fails on a bound r5/r7 reference, multi-request concurrency is not necessary for that failure. Next inspect
  arithmetic/reference ordering at the first failed boundary; do not run the four x8 variants to claim a race.
- If x1km passes but x8 fails on both invocations, the failure depends on the multi-request path under these conditions.
  Recipe is better controlled, but scheduling, register spills and payload visibility remain distinct hypotheses;
  this does not prove a race. Then prepare a separate, bounded x8p/x8m/x8k/x8 diagnostic using distinct binary hashes.
- If x8 passes twice, report failure not reproduced on the newly certified inputs. This neither repairs nor invalidates
  the historical failure. Preserve the result and decide whether repeat/slot-permutation evidence is needed.
- If outcomes differ between repeats or provenance is incomplete, report unresolved and stop; do not select a winner.

A successful diagnostic produces a reproducible classification, not necessarily a passing x8 arm. No throughput
number, numerical fix or hardware-offset claim is an acceptance condition.

## Later performance experiment: separate decision

B4 is a separate open question. The modeled useful payload is 19.738 GB/step at context 1024, or 4.590 ms at an
assumed 4.3 TB/s; historical ETX/vLLM wall medians are 9.760/7.054 ms. The measured HBM traffic and current trace's

cause or authorize column-batched tiles. Before building such tiles, capture gated B1/B2/B4 traffic, body/wait spans
and exact-prefix routing, then recompute the existing build trigger with the repaired parser. No speculative new
optimization is included in the correctness budget.

Any later speed claim needs both the same-kernel HIP-graph comparison and the strongest tested legal vLLM baseline,
on the same GPU/session with five interleaved pairs and complete correctness evidence. Qwen fusion retains its
registered rule: every wall gain positive, median above 2% and above twice the spread, 32/32 tokens and same-build
import checks. These diagnostic runs do not re-establish that claim.
