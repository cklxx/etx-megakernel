# Survey 2026-09-29: what the public record says about our three open questions

Written while waiting for a VM. M = measured in the source, S = vendor spec, D = documented behaviour.
Question 1: is layer pipelining across XCDs worth building? Question 2: where does a ~2 us per-task tax come
from and how do other megakernels hide it? Question 3: where does our vLLM baseline (4.67 ms per token,
Qwen3-30B-A3B bf16, one MI300X) sit against the public numbers?

## 1. One XCD's share of the memory system (decides pipelining)

- [M] One XCD in SPX/NPS1 streams about 0.5 TB/s, the same per-XCD rate whether or not the other XCDs are
  active; the whole GPU 4.0-4.2 TB/s. In NPS4 an XCD alone on its IOD reaches ~1 TB/s (two HBM stacks), back to
  ~0.5 when its sibling streams too. The XCD-IOD link (2.1 TB/s, S) is not the limit; per-XCD outstanding
  misses are. https://rocm.blogs.amd.com/software-tools-optimization/compute-memory-modes/README.html
- [M] Infinity Cache 11.9 TB/s (17 theoretical), ~218 ns hit; address-sliced per HBM stack and shared by all
  XCDs in NPS1, so an activation written back with wbl2 is read by another XCD at MALL latency, not HBM.
  https://chipsandcheese.com/p/testing-amds-giant-mi300x, https://escholarship.org/content/qt3b8311qq/qt3b8311qq.pdf
- [M] Atomic ping-pong 116 ns same XCD, 203 ns across XCDs (atomics execute in L2). Our own: release/acquire
  115/137 ns, one cross-XCD hop 703 ns (fleet-amd-task PR #5).
- [D] SPX places workgroups round-robin over XCDs with no pin API; the start offset is not guaranteed (we saw
  (k+4) mod 8), so placement must read XCC_ID, which ETX does. CPX is the only true pin.
- Not found: 2 or 4 XCDs streaming in SPX (hw_bench lfx measures it); buffer_inv sc1 / wbl2 cost vs dirty lines.

Consequence (docs/MODEL-vllm-kernels.md section 17): pipelining does not add bandwidth on one GPU; it only
removes the device-wide hand-off premium (~0.4 ms per token) and gives up the weight reuse of batching.
Batching wins at every batch size and stage count in the analytic model. Order: batching (B <= 8), then the tax.

## 2. Megakernels: scheduling, signalling, and the per-task cost they report

| system | schedule | signal | overhead (M) | gain (M) |
|---|---|---|---|---|
| Hazy No Bubbles (Llama-1B, B200/H100) | static per-SM instruction list | global counters, spin | ~120 of 600 us pass in sync + setup | 2.5x vLLM, 78% HBM BW, BS 1 |
| Hazy 70B / Tokasaurus (8xH100) | global atomic queue (tasks >= 100 us) | flags per output | gap between matmul instructions 10.2 -> 3.4 us with cross-instruction pipelining | +22% vs SGLang |
| ThunderMLA | static, host scheduler | tensor semaphores | removed ~2 us kernel latency per partial | 20-35% over FlashMLA |
| Mirage MPK | per-SM queues + 4 scheduler SMs; AOT + JIT tasks | event counters | scheduler 0.28% of runtime; 352 B descriptor prefetched into smem | 1.0-1.7x vLLM/SGLang, NVIDIA only |
| ForgeMegakernel | per-SM typed streams, interpreter | counter semaphores | SGLang launch 4.63 us; sync per token 333-851 -> 227-313 us | 1.21x SGLang; icache and descriptor fetch left unaddressed |
| Cohere North Mini (30B MoE, H100) | static waves + local work stealing | count-based, nanosleep(20) | weights prefetched before the activation dependency | 292 tok/s BS 1, 1.58x vLLM |
| Kog monokernel (MI300X, closed) | fully static, no queue | sentinel on data (NaN pre-fill), no atomics, no fence | sync 0.80-0.93 us vs 7.6-7.9 us with counter + fence; grid sync was 35% of the token | 3000 tok/s BS 1 on 8 GPUs, 2B model |
| AMD Fleet (MI350, MPK-derived) | one scheduler WG per XCD, per-worker queues | intra-XCD device-scope atomics in L2 without fence; cross-XCD one wbl2 + atomic sc0 sc1 per XCD | cross-XCD signals 25,200 -> 1,830 per step | 1.54x vLLM at bs 1, 1.06x bs 32, slower at bs 64; "scheduling overhead is the bottleneck at bs 1-16" |

Sources: hazyresearch.stanford.edu/blog (2025-05-27, 2025-09-28, 2025-03-04, 2026-02-19), arxiv 2512.22219,
2609.12379, 2604.13327, 2605.11581, 2505.22758, 2604.15379, cohere.com/blog/megakernels, blog.kog.ai.

What applies to a 1.4-2.9 us per-task tax on gfx942:
1. Nobody beats the launch boundary by scheduling alone; the wins are (a) fewer fences and atomics on the hot
   path and (b) the next task's loads overlapping the current task's tail (Hazy: 10.2 -> 3.4 us from that alone).
2. The only MI300-class numbers bracket ours: counter + fence 7.6 us, sentinel on data 0.8 us. First split our
   tax into fence / atomic / descriptor fetch / wave start; no public gfx942 breakdown exists.
3. Match the counter's scope to the data's scope: intra-XCD edges resolve in L2 without a fence; only the last
   worker per XCD touches a device-scope counter (Fleet). Our head-affine attention block already keeps its
   edges inside one XCD; the GEMV -> GEMV edges do not yet.
4. Weights depend on nothing: start the next task's weight stream before its activation event completes
   (Cohere, Hazy, MPK's descriptor prefetch). This is the mechanism that hides a 2 us boundary entirely.
5. Static per-CU queues beat dynamic ones at BS <= 16; scheduler hops cost more than a 2 us task. Keep AOT
   enqueue and direct event waits.
6. Coarser tasks amortise the fixed cost (Fleet's chiplet task = one GEMM per XCD; MPK's 0.28% comes from
   tens-of-us tasks). Fewer, larger tasks for the small ops.
7. Even the best NVIDIA systems keep 15-25% of a BS 1 pass in sync and setup; gains vs vLLM/SGLang are
   1.2-1.7x and come from overlap and bandwidth, not from the removed boundaries themselves.

## 3. Where 4.67 ms sits

- No published batch-1 Qwen3-30B-A3B number on MI300X from AMD, vLLM, SGLang or aiter. Nearest: Qwen3.6-35B-A3B
  FP8 + MTP on one MI300X, 14 ms per step (millstoneai.com); H200 vLLM FP8 Coder-30B-A3B 165 tok/s; H100 FP8
  35B-A3B 212 tok/s; H20 BF16 SGLang 137 tok/s (qwen.readthedocs.io speed benchmark).
- 6.1 GB streamed per token -> 4.67 ms = 1.3 TB/s = 25% of 5.3 peak, 30% of the 4.3 TB/s copy ceiling
  (BabelStream, arxiv 2510.27583). Every public batch-1 MoE datapoint on gfx942 sits at 20-26% (vLLM, fleet,
  vkernels, stock fused_moe) except Kog's persistent kernel at 36%. Nobody has published above 36% at batch 1.
  Build 3 predicted 3.93 ms = 29%; floor 1.4 ms at 4.3 TB/s, 1.75 ms at the 3.5 TB/s kernel authors call attainable.
- Baseline fairness: vLLM main ships no bf16 E=128,N=768 MI300X fused_moe config, so stock bf16 runs the default
  heuristic unless VLLM_ROCM_USE_AITER=1 (aiter / FlyDSL, AMD's current default route; Qwen3.5-35B shapes at
  B=1: 30.4 -> 11.5 us per fused_moe call, github.com/ROCm/aiter/pull/3987). Already measured (results_2026-09-27,
  same model, batch 1): aiter on 4.916 ms vs default 4.836 ms, so the default baseline stands.
- Per-kernel cost on MI300X ~4.5 us launch + ~0.5 us HBM restart (Kog); hipGraph per-node replay gap is not
  published; our 1.61 us kernel boundary is a new number.
