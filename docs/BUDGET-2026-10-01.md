# Per-phase budget, 2026-10-01 (decode traces)

What each phase of one layer costs, against what its own bytes and width say it should cost, so the residuals pick
the next target rather than a guess. Five mechanisms proposed during the day were refuted by these measurements;
the settled list at the end exists so none of them is retried.

**This version rests on a decode trace.** The previous version derived every per-phase number from a trace taken
with `--max-steps 8`, which stops inside the teacher-forced prompt where `seq_len <= 8`. What changed:

- `attn`'s body is **6.28 us, not 1.91** — in the prompt regime partitions 1..4 hit the imported kernel's
  `partition_start_token_idx >= seq_len` early exit, so 16 of 20 tasks returned immediately. The "4.3x partition
  imbalance" the old version reported does not exist in decode (all 20 bodies 5.7-6.7 us).
- The weight-streaming phases are unaffected, as expected, since they do not depend on sequence length:
  `qkv` 6.62 vs 6.66, `moe_up` 20.03 vs 20.03 across the two regimes.
- The build also changed: this is the post-round-7 `FOLD_TOPK=0` build, which has a separate `topk` phase
  (9 phases per layer, not 8) and much smaller MoE bodies.

Build: switch set B (XCD, CHAIN, DSL_GEMV, DSL_TOPK, DSL_ATTN=head, FOLD, TOUCH, COH) with `ETX_VL_FOLD_TOPK=0`
at `ETX_VL_CU=256`, on the MI300X VF box (ROCm 7.14). **5.056 ms/token untraced**, 5.073 with tracing on, 32/32
tokens + CHECK-DSL OK. Trace `results_2026-10-01/round11/trace_r11_decode.bin` (60362 tasks, total span 5081.5 us),
plan `results_2026-10-01/round11/plan_r8base.json`. Per-phase values are the mean over layers 1..45; layer 0 carries
the prologue and the unfolded `in_norm`, and the last layers run into `lm_head`.

## What the trace columns are

From the raw trace (nine int64 per task: type, coord[0..3], taken, deps-ready, body-done, worker; 10 ns ticks) and
`dump_phase_trace` in `etx/runtime/include/etx/host.h`:

| quantity | definition | what it bundles |
|---|---|---|
| `wait` | deps-ready − taken | event poll **+ acquire + ctx/prologue setup + one barrier** |
| `body` | body-done − deps-ready | the tile body **+ the all-wave `ETX_RELEASE_DOMAIN` drain + one barrier** |
| `critical body` | body of the task with the largest body-done | what the phase actually waits for |
| `start delay` | that task's deps-ready − the phase's first deps-ready | when the critical task got going |
| `delta` | next phase's first deps-ready − this phase's first deps-ready | the phase's real cost in the chain |

Two things the columns cannot do. `wait` is **not** attributable to the event protocol: it also holds the acquire,
the argument setup and a barrier, and for a phase not yet due it is mostly legitimate idling (`o_proj` waits 24.7 us
while the attention block runs — that is not a cost). The **arrive is in neither column**; it falls between one
phase's last body-done and the next phase's first deps-ready, so it is inside `delta`. Everything below uses
`delta`, which is why the phase deltas sum exactly to the layer period.

## The achievable rate

From `results_2026-10-01/hw_stream.log` on this box, `contig` mapping (`dsl_gemv_rows` gives each task a contiguous
`[r0, r1)` row range, so `contig` is the right comparison; `rows` is headroom we do not take). Per-workgroup rate =
bytes per workgroup / (phase span − 3.0 us floor): `gate_up x192` gives **19931 B/us at width 192** (measured);
interpolating the `gate_up` and `o_proj` width pairs to 256 gives 13249 and 11458, and I use the mean,
**12354 B/us at width 256** (±7%, *interpolated, not measured*).

Caveats that make this an estimate: `hw_bench` uses 256-thread workgroups where ETX uses 1024; its `grid_barrier`
runs `buffer_inv sc1` every pass, so its rates are cold-start — which matches a pre-COH megakernel and does not
bias weight phases (6.08 GB/token is never cache-resident) but understates what a COH phase reaches on cached data.

## Classification

**At the achievable rate — done, do not work here.** `o_proj` (103% of achievable), `attn` (MALL-resident),
and the GEMV part of `qkv`: layer 0's *unfolded* `qkv_0` body is 6.66 us against 6.63 achievable, i.e. 100%.

**Residual with a known cause.**

- `qkv` 5.39 us/layer — the folded norm. `qkv_0` (unfolded) 6.66 vs `qkv_L` (folded) 11.84. **This is a wash, not
  an opportunity:** the fold replaces the `in_norm` phase, whose own body is 3.89 us plus ~1.0 us of hand-off, so
  folding costs +0.28 us/layer net (+0.013 ms/token). Recorded so it is not re-litigated in either direction.
- `router` 3.42 us/layer against 0.17 achievable, and its critical body (7.32) is double its mean (3.59) because
  128 of its 256 tasks have no row to compute at `CU=256` (M=128). The phase is bounded by one real task doing
  4 KB of weights in 7.32 us — latency and the fold, not bytes. The `CU` sweep (round 2) already bounded what
  narrowing recovers at 0.067 ms overall.
- `prep`/`reduce` 5.85 + 5.57 us/layer = 0.548 ms/token — dependent chains of 8.5 and 8.1 hops against ~3-4
  structurally necessary. Task-boundary redraws are **ruled out** (see settled list); the lever is the chain
  inside the tile, and in-place reordering already failed on register pressure.

**Residual with an unknown cause — ranked by size, with the cheapest deciding measurement.**

1. **`moe_up` + `moe_down`, 11.09 us/layer = 0.532 ms/token** (66% and 65% of achievable). Round 6 excluded the
   expert gather (~7%) and round 7 excluded the epilogue (1.4 us/layer) and removed the top-k fold. What remains
   is spread across LDS staging, the two chunked passes and the 16-wave partial reduction, with no single
   candidate above 30%. *Deciding measurement:* none is cheap — this is the tile-redesign call, not a probe.
2. **`topk`, 8.14 us/layer = 0.391 ms/token**, for a 128-logit softmax and an 8-way selection over 8 tasks. It is
   11.8 dependent round trips for 64 B of input. This phase was re-introduced in round 7 (it still won 0.231 ms
   net by deleting 14.1 us/layer of redundant recompute), but nobody has looked at the tile itself since.
   *Deciding measurement:* one ablation build with the selection replaced by a fixed answer, timing-only, ~20 s —
   separates "the scan is slow" from "the phase is 8 tasks of pure latency".
3. **`qkv` start spread, 0.048 ms/token** — the only ETX-attributable part of the start delay. *Deciding
   measurement:* re-order the static queue so `qkv`'s tasks are not the tail of the previous layer's `moe_down`
   on each worker; the plan already controls this in `p5_queues.py`.

## Round 13: `topk` (0.391 ms/token) is settled — bound by publishing its output, not by the scan

All 8 tasks compute the same softmax + top-8 over the same 128 logits, one per XCD, each writing its XCD's copy
(the rematerialisation of model.py:91). They run in parallel, so the phase costs one body, not 8x anything —
**fewer replicas cannot help**, and would make the downstream hand-off device-wide.

Timing-only ablations (each diverges at token 0 by design, so none was optimised away; ±0.006 within a binary):

| variant | ms/token | delta | removes |
|---|---|---|---|
| ctrl | 5.050 / 5.054 / 5.056 | — | — |
| noload | 5.003 | −0.042 | the 2 coherent logit loads |
| nostore | 4.822 | **−0.223** | all 24 coherent output stores |
| skip | 4.746 | −0.299 | loads + scan (stores kept, back to back) |
| notei | 5.044 / 5.052 / 5.050 | **−0.004** | 8 of the 24 stores (`tei`, read by nothing) |

The scan is trivial (loads 0.042, arithmetic less). The body is the **coherent publication** of the outputs, and
it is not per-store: removing a third of the stores buys 0.004 while removing all of them buys 0.223 — one
write-through round trip that every store sits behind (~4.6 of the 8.14 µs body).

Tried and **negative**, do not retry (numbers in `etx/ops/topk.py`, commit 55eba53):
- **Batching the stores** into one end-of-tile burst: +0.008 ms, consistently. `skip` was cheap because it dropped
  the loads and the scan, not because its stores were ordered differently.
- **Dropping `tei`** (vLLM signature parity; host.hip:241 voids it, the MoE tiles take only ids/weights): −0.004,
  inside the spread — not worth the signature divergence.

The only remaining lever is not publishing coherently, which reintroduces the consumer-side `buffer_inv sc1` that
round 1 removed for a far larger gain. Classification: **(b) tile quality, at its floor given the COH design.**

## Utilisation (round 15, rocprofv3 on the MI300X VF box)

Counters read per kernel by joining `rocpd_pmc_event` to `rocpd_kernel_dispatch` and filtering to
`etx_megakernel_d0` — the run also issues 12,807 rocclr copy/fill dispatches (36.6 ms of 5337 ms) that ruin
any unfiltered average. `rocprofv3` SIGSEGVs at teardown after writing its database; the data is intact.

**Occupancy is exactly half, and both resources bind at once.** `MeanOccupancyPerActiveCU` = 4.000 (min = max,
all 1055 dispatches) against the hardware's `max_waves_per_simd: 8`; `OccupancyPercent` 49.3; `MeanOccupancyPerCU`
3.946, so ~98.6 % of CUs are occupied. VGPR: 512/SIMD ÷ 128/wave = 4. LDS: 65536 ÷ 41448 = 1 workgroup = 4/SIMD.
Because the VGPR term is 4 regardless of workgroup size, **smaller workgroups cannot raise occupancy on their
own** — two 512-thread workgroups give the same 16 waves/CU. Reaching 6 waves/SIMD needs VGPR ≤ 85 *and*
LDS ≤ 21845 B together; 8 needs ≤ 64 and ≤ 32768 B. The megakernel is at 128 VGPRs with 15 spills, so this is a
tile redesign, not a flag. Not attempted.

**86 % of wave-cycles are spent waiting, with the memory unit idle.** `SQ_WAIT_ANY` 303.8 M of `SQ_WAVE_CYCLES`
353.8 M = 85.9 %; `MemUnitStalled` 0.0; `LdsBankConflict` 0.3. Waiting while the memory pipe never backs up means
too little memory-level parallelism, not too little bandwidth — which is the same finding as the occupancy cap,
seen from the other side.

**The instruction cache is not a problem.** `SQC_ICACHE_HITS` 6,815,943 vs `MISSES` 6,958 per (dispatch,
instance) = **99.90 % hit rate**, 222,666 misses per token (~14 MB, 0.2 % of the weight stream). The literature
(ForgeMegakernel) names icache thrashing as an unaddressed megakernel cost; our single switch over ~400 task
types does not suffer from it. Ruled out.

**L2 was being polluted by weights that are read once — fixed, and it is this round's shipped win.** Control:
`TCC_HIT_sum` 23.84 M, `TCC_MISS_sum` 50.93 M → **31.9 % hit rate**; `TCC_EA0_RDREQ_DRAM_sum` 50.87 M, i.e.
99.9 % of misses become fabric reads, at 119.5 B per request for 6.08 GB — no read amplification. Weights have no
reuse yet evict what does (the 104 MB MALL-resident KV cache, the activations). `ETX_VL_NT=1` marks the DSL
GEMV's weight loads non-temporal (`dsl_wload` / `__builtin_nontemporal_load`; coherent activation accessors and
imported kernels untouched):

| | control | ETX_VL_NT=1 |
|---|---|---|
| L2 hit rate | 31.9 % | **34.6 %** (hits +8.8 %, misses −3.9 %) |
| DRAM read requests / token | 50,867,626 | 48,907,452 (−3.9 %) |
| ms/token, 3 runs | 5.034 / 5.022 / 5.021 | **4.916 / 4.911 / 4.916** |

**−0.106 ms/token (−2.1 %)**, 35× the ±0.003 within-binary spread; 32/32 tokens and CHECK-DSL both pass; unfused
5.088, so fusion still wins by 0.172 ms. Left **off by default** — flipping it is one line.
