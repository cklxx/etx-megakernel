# ETX_TOPK_KEY32: top-k selection on one 32-bit key per expert (2026-10-08)

This document describes a new compile switch for the softmax top-k. The box has no GPU. All results are CPU emulation and static ISA counts. This document does not claim a runtime gain.

## 1. Result

- `ETX_TOPK_KEY32=1` selects the top-k ids on one 32-bit key per expert. A DPP wave max replaces the `ds_bpermute` butterfly in each round.
- The switch is off by default. On `ae1529c` plus the port patch (section 7), the switch-off build is the MATCH build. The resource fingerprint is equal, and the instruction stream is identical (112,693 instructions, 0 different lines).
- This is not true on this PR branch. The PR parent `11db891` is 123 commits after `ae1529c` (for example, `d0f41ab` changed the LDS size). On the branch, the switch-off build has VGPR spill 9, LDS 29,736 B and 95,787 instructions, against 14, 41,448 B and 112,693 for MATCH. On the branch, compare the switch-on build against the switch-off build of the same commit, not against MATCH.
- On `7a780b4` (fix, `verify_flag.sh`), switch on and switch off have the same resources: unfolded 128 VGPR / 40 SGPR / 9 spill / 29,736 B LDS, fold 128 / 36 / 8 / 29,736 B. The on builds have 36 and 24 DPP instructions and 0 DPP hazards.
- With the switch on, VGPR, SGPR, spill, scratch and LDS do not change. This is true in the MATCH configuration (unfolded top-k) and in the fold configuration (`ETX_VL_FOLD_TOPK=1`, reference `MATCH_fold_loc`). Section 7.4 gives the fold numbers.
- The topk selection loop has 0 `ds_bpermute` and 0 `s_waitcnt`. One trip has 39 instructions. Before the change, one trip had 182 instructions, 12 `ds_bpermute` and 24 `s_waitcnt`.
- The global hop chain of the topk phase does not change. It has 4 hops (1.21 us at 0.50 us).
- lucky's independent checker has 25,004 rows. Each row runs with and without renorm (50,008 runs). The ids are equal to the old path in all runs, except the runs of 2 adversarial rows. Section 5 explains those 2 rows.

## 2. Switch

- Build: `ETX_TOPK_KEY32=1 bash examples/vllm_llm/build.sh <model>`. build.sh then adds `-DETX_TOPK_KEY32`. The plan does not change.
- Code: `etx_topk_key32` and `etx_topk_key32_lds` in `etx/runtime/include/etx/tile_util.h`. The block is inside `#ifdef ETX_TOPK_KEY32`. Both functions use one body (`etx_topk_key32_impl`). Section 3.4 describes the two output forms.
- Guards for the switch-on build:
  - The key path needs K <= 64, because lane t keeps the result of round t. `host.hip` stops with `die()` when the switch is on and TOPK > 64. `host.hip` already refuses E > 128.
  - `ETX_ABL_TOPK_NOSTORE` has no effect on the key path, so `topk.py` has an `#error` for the switch together with `ETX_ABL_TOPK_NOSTORE`. `ETX_ABL_TOPK_SKIP` and `ETX_ABL_TOPK_NOLOAD` still work.
- Callers: `dsl_run_dsl_topk` in `etx/ops/topk.py` (the topk phase) and `dsl_topk_lds` in `etx/ops/gemv.py` (the top-k fold). Each call is inside `#ifdef ETX_TOPK_KEY32`. The old code is in the `#else` branch or after the call.
- With the switch off, the preprocessor removes every new line. `tests/test_topk_key32.py::test_switch_guards_every_key32_line` checks this.
- The sparsemixer mode (mode 2) does not change. Only modes 0 and 1 take the key path. The key call comes after the mode-2 branch returns. In `topk.py`, the switch removes only the `etx_wave_max(m)` call before the mode-2 branch. The mode-2 code does not read that `m`. `test_sparsemixer_mode_is_unchanged_by_the_switch` checks this. The CPU checkers do not cover mode 2.
- MATCH runs the unfolded top-k (`ETX_VL_FOLD_TOPK=0`). The executed function is `dsl_run_dsl_topk`. The 2 inlined copies of `dsl_topk_lds` in the moe fold tiles do not run in that plan. The switch changes both functions.
- The `tei` stores stay. They have no reader (`host.hip` voids them), but the switch changes only the selection. The outputs are the same as the old path.

## 3. Design

### 3.1 Key

- The key is `bit 23 (valid) | order16(logit) << 7 | (127 - e)`. Key 0 means "taken" or "e >= E".
- `order16` is offset binary: `0x8000 + magnitude` for a positive logit, `0x8000 - magnitude` for a negative logit. The magnitude is the low 15 bits of the bf16 value.
- -0 and +0 both give 0x8000. They tie, and the smaller index wins. The old path does the same, because the float compare sees -0 == +0.
- The code tests NaN explicitly (`x != x`). NaN gives order 0, below -inf (0x0080). The bit mapping alone puts a positive NaN above +inf, so the explicit test is necessary.
- The unsigned max of the keys gives the largest logit. On equal logits, the smaller e has the larger low field and wins. This is vLLM's tie rule.
- The low field has 7 bits, so E must be 128 or less. A `static_assert` in `tile_util.h` checks the lane layout (2 logits per lane, 64 lanes). `host.hip` already refuses E > 128 for `dsl_topk` and for the folds. The Python emulation raises an error for e >= 128.
- The valid bit makes every real key nonzero. Without it, a NaN at e = 127 has key 0.
- The order of all valid keys is the same as in lucky's specification (`check_key32.py`, which uses `~b` for a negative value and canonical -0). Only the constant offsets are different.

### 3.2 Softmax is not on the selection chain

- Softmax is monotone. The ids therefore come from the raw logits.
- The round-0 winner is the max logit m. `etx_key32_logit` decodes it from the key. The old `etx_wave_max` of the floats is not necessary.
- After round 0, the code computes `p = expf(l - m)`, `s = etx_wave_sum(p)`, `inv = 1 / s` and `p *= inv`. These are the same operations, in the same order, as the old path. The sum keeps the old butterfly, so the weights are bit-identical in intent.
- Each round reads the weight with `v_readlane_b32` from the winner lane's p. The rounds sum the weights in round order. With renorm, the weight is `w / sel`, as in the old path.
- vLLM 0.27.1 renormalizes with `w * (1 / sel)`. The old ETX path uses `w / sel`. The switch keeps the ETX arithmetic. This is a known difference of up to 1 ulp. It is not new.

### 3.3 DPP wave max

- Steps: `row_shr:1`, `row_shr:2`, `row_shr:4`, `row_shr:8` with `bound_ctrl` (an invalid source reads 0, the identity of the unsigned max). Then `row_bcast:15` with `row_mask 0xa` and `row_bcast:31` with `row_mask 0xc`. Then `v_readlane_b32` reads lane 63 into an SGPR.
- We chose `row_mask 0xa` and `row_mask 0xc`. lucky's DPP model shows that the full row mask also gives the correct max.
- The code uses `__builtin_amdgcn_update_dpp`. It does not use inline asm. The compiler combines each step into one `v_max_u32_dpp` and inserts `s_nop 1` for the gfx9 wait states. fix's `topk_isa.py` hazard check finds 0 hazards in the on build.
- The winner lane clears its key to 0. The loop runs K rounds. The compiler peels round 0.
- Lane t keeps the result of round t. At the end, lanes 0 to K-1 store their id and weight. This needs no array with a runtime index. A first version kept `lw[16]` in each lane. That array cost 16 VGPRs and gpr-index moves in each round.
- We did not implement a bitonic sort.

### 3.4 Two output forms

- `etx_topk_key32` (lane t form): lane t keeps the id and the weight of round t. Lanes 0 to K-1 store at the end. `dsl_run_dsl_topk` uses this form.
- `etx_topk_key32_lds` (lane 0 form): lane 0 stores the id and the weight in each round. The function returns sel. With renorm, lane 0 then divides each weight by sel, as the old `dsl_topk_lds` code does.
- The two forms give the same ids and the same weight bits. The host SIMT test runs both forms and compares the output bits.
- `dsl_topk_lds` selects the form at compile time:
  - When the plan folds the top-k (`ETX_EMIT_FOLD_TOPK` = 1), `dsl_topk_lds` runs and uses the lane 0 form.
  - When the top-k has its own phase (`ETX_EMIT_FOLD_TOPK` = 0, the MATCH configuration), `dsl_topk_lds` does not run and uses the lane t form.
- The reason is register allocation only. The kernel uses 128 VGPRs, the limit, so a small change in any inlined code can move spills to a different tile. Each form keeps the switch-off spill count in its own configuration. The other form adds 1 or 2 spilled VGPRs there (section 7.4).
- On `ae1529c` the plan does not publish `ETX_EMIT_FOLD_TOPK`. The ISA patch therefore tests `!defined(ETX_VL_NO_TOPK_FOLD)`, which build.sh sets from the same `ETX_VL_FOLD_TOPK` value.

## 4. Numerics check (CPU)

- `etx/ops/topk_key32.py` has two emulations. `ref_topk` is the old path. `key_topk` follows `etx_topk_key32` line by line. Both use float32, 64 lanes, the same exp, and the butterfly sum of `etx_wave_sum`.
- `tests/test_topk_key32.py` has 16 tests:
  - `order16` keeps the float order for all 65,536 bf16 values. Equal keys occur only for -0 and +0. NaN gives 0.
  - `key32_logit` inverts the key for all bf16 values.
  - The DPP model gives the max of 64 lanes.
  - Selection on E128-K8, E64-K6, E8-K2, E128-K1 and E128-K16. The rows have normal values, heavy ties, wide ranges, -inf and -1e30. The ids and the weights are equal to the old path. Where they are not equal, the old path has equal float p for the two experts.
  - ±0 rows select ids 0 to 7.
  - One NaN, one exp-underflow tie and one rounding tie (section 5).
  - A host SIMT harness (`tests/data/topk_key32_simt.cpp`) compiles the C++ block of `tile_util.h` with g++. 64 host threads run it as 64 lanes. It runs both output forms. The ids are equal to the emulation. The weights agree to 4e-7 (host exp is not numpy exp). The two forms give the same bits.
  - The build guards of section 2 exist and are inside `#ifdef ETX_TOPK_KEY32`.
- lucky's independent checker (`/workspace/topk_check/check_key32.py`) has 25,004 rows, each with and without renorm (50,008 runs). `isa_r11/TOPK_KEY32/run_lucky_checker.py` runs them against `key_topk`:
  - The ids are equal to lucky's `key_topk` in all 50,008 runs.
  - The ids are equal to the old path in 50,004 runs. The 4 other runs are the "underflow" and "one-nan" rows (each with and without renorm).
  - The weights agree with lucky's emulation to 1e-6. lucky sums p with numpy, not with the butterfly, so the last bit can differ.
  - Inside one emulation (same butterfly sum), the weights are bit-identical to the old path, except in the 4 runs above.
- The same 50,008 runs also go through the C++ block itself (`isa_r11/TOPK_KEY32/run_lucky_simt.py`, the host SIMT harness, both output forms):
  - The ids are equal to lucky's `key_topk` in all 50,008 runs, for both forms.
  - The two forms give bit-identical ids and weights in all runs.
  - The weights agree with lucky's emulation to 1e-6 in all runs.

## 5. Differences from the old path

1. Exp underflow (adversarial). `expf(l - m)` is 0 when `l - m` is less than about -104. The old path then sees equal p (0) and takes the smallest indices. The key path takes the largest logits. The weights are 0 in both paths. For E = 128 and K = 8, this needs at least 121 experts with underflow. For E = 8 and K = 2, 7 experts must underflow.
2. Rounding tie. Two different logits can give the same float `l - m` when `|l|` is less than about 2^-17 `|m|`. The old path then takes the smaller index. The key path takes the larger logit. The two weights are equal. The test `test_rounding_tie_difference` shows one case (m = 20, l about 1e-6).
3. NaN. Section 6 describes the old path. The key path selects the K largest finite logits. The weights are NaN in both paths, because s is NaN.
4. Fewer than K valid experts (E < K, or all NaN). The old path writes 0x7fffffff. The key path writes expert 0 when no key is left. Both are outside the contract (host.hip requires E >= K).

## 6. Existing NaN bug (switch off, not changed)

- With one NaN logit, `dsl_topk_lds` and the softmax path of `topk.py` write ids 0x7fffffff. That value is not a valid expert id.
- Cause: `s` is NaN, so every p is NaN. No lane passes `p > bv`. `bi` keeps its initial value 0x7fffffff.
- Only the sparsemixer path guards the index (`topk.py:77`, `if (bi < 0 || bi >= E) bi = 0`).
- vLLM 0.27.1 sets a NaN or inf softmax value to 0 (`topk_softmax_kernels.cu:460-471`), so it selects valid ids.
- We did not change the switch-off path. It must keep the switch-off build unchanged (the MATCH fingerprint on `ae1529c`). `test_one_nan_logit` records the bug.

## 8. What a GPU run must measure

1. Correctness. Build with `ETX_TOPK_KEY32=1`. Run the 32/32 token gate against the HF greedy reference for Qwen3-30B-A3B (E128-K8). Also run it for an E=64 and an E=8 model if the matrix has them.
2. Bit check. Dump the topk ids and weights of each layer for the switch-off build and the switch-on build. The ids must be equal. The weights must be bit-identical.
3. topk body. Trace both builds with the same plan. Compare the topk body (tr[1] -> tr[2]) per task. The FLOORS value is 8.35 us for the body and 1.21 us for the chain.
4. Other bodies. Compare the bodies of attn, reduce, prep, moe_up and moe_down. The register allocation changed there.
5. Total. Measure ms per token with interleaved A/B pairs (`examples/vllm_llm/pairs.py`).
6. Fold configuration. Repeat items 1, 2, 4 and 5 with `ETX_VL_FOLD_TOPK=1`. Compare the moe_up and moe_down fold bodies, which contain the top-k there.

## 9. Risks

1. No device ran this code. The DPP semantics come from the ISA documentation, the host SIMT model and lucky's model. fix confirmed that the modifiers assemble with the matching compiler.
2. The device `expf` is the same call with the same inputs in both paths. We expect bit-identical weights. A device test must confirm this.
3. The ISA pairs are from `ae1529c` plus the patch, not from this branch. `verify_flag.sh` on this branch is a compile check only. Its off build cannot reproduce MATCH, because the branch changed other tiles after `ae1529c`.
4. The exp-underflow and rounding ties of section 5 change ids in adversarial rows. The weights stay equal.
5. The kernel uses 128 VGPRs, the limit. A small change in any inlined code, also code that does not run, can move 1 or 2 spilled VGPRs to a tile that runs (section 7.4). The choice of output form is correct for this tree and this compiler. A later change of the kernel or the compiler can change the result. Run `verify_flag.sh` for both configurations after such a change.
6. The ae1529c patch selects the form with `ETX_VL_NO_TOPK_FOLD`. The branch selects it with `ETX_EMIT_FOLD_TOPK`. The two macros come from the same `ETX_VL_FOLD_TOPK` value, but the branch form was compiled only as part of the branch compile check.
