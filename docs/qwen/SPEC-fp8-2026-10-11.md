# Spec: FP8 weights for Qwen3-30B-A3B on one MI300X, 2026-10-11

Repository `56e34c4`. vLLM sources: `~/code/vllm/` (`f46a9dfe2`); `SG` = `csrc/rocm/skinny_gemms.cu`, `VL` = `vllm/model_executor/`.
`FLOORS` = `docs/qwen/FLOORS-2026-10-08.md`, `LEVERS` = `docs/qwen/LEVERS-300TOKS-2026-10-11.md`, `SCOPE` = `docs/SCOPE-300TOKS-2026-10-11.md`.
This spec changes no code, spent no GPU time and makes no performance claim.
Labels: [measured] = a command ran today on this laptop; [hf] = read today from the Hugging Face API or a `config.json` fetched from it; [source] = read from code; [arith] = arithmetic on the cited numbers; [estimate] = a model, not a measurement; [unknown] = nobody has measured it.

## 1. The question and the answer

Can FP8 weights take ETX's batch-1 decode from 4.471 ms (223.7 tok/s, `SCOPE:25`) to 3.333 ms (300 tok/s)?

- FP8 halves the bytes of the four weight phases. The step drops from 6.190 GB to **3.473 GB** [arith, section 3]. lm_head stays bf16 in every published checkpoint, so the step does not halve.
- The new floor is **0.81 ms at 4.3 TB/s**, 0.93 ms at the measured stream rates. The floor is not the limit. Today's step is 4.471 ms against a 1.67 ms bf16 floor at the same rates [arith].
- The deciding unknown is how fast the DSL tile bodies become. The in-tile ablation shows that the MoE tiles are skeleton-bound: with no weight stream at all, a body still costs 63% (up) and 69% (down) of the control (`etx/ops/gemv.py:17-29`) [source]. Halving the bytes therefore cannot halve these bodies on today's tile structure.
- Estimate: FP8 takes the step to between **4.13 ms (242 tok/s)** and **3.49 ms (287 tok/s)**. It reaches 300 tok/s only if the four weight bodies drop to 52% of today, together with the 0.19 ms of other levers (`LEVERS:95`) [estimate, section 3.3]. That needs fp8 tiles and a cheaper MoE skeleton.
- Recommended recipe: **weights per output channel (PTPC weights), activations kept bf16 (W8A16) in ETX**. Take the weights from the published `RedHatAI/Qwen3-30B-A3B-FP8-dynamic` checkpoint; no quantization run of our own. Gate correctness against HF greedy on a bf16 checkpoint dequantized from those exact fp8 weights (section 5).
- FP8 changes the claim in `CLAUDE.md` section 1 (`SCOPE:66`): the golden is no longer the bf16 model's. The owner decides that. Stage 0 and Stage 1 (section 7) are microbenchmarks that need no decision about the claim.
- First edit regardless of FP8: the loader must refuse any `quantization_config`. Today it plans an FP8 config exactly like bf16 (`434 e68e856650430532`) [measured], and `prep.py` would pack raw fp8 bytes as bf16 with no scales (`examples/vllm_llm/prep.py:78`, `:88`) [source].

## 2. Recipe (question 1)

### 2.1 The checkpoints that exist

| checkpoint | weights | activations | not quantized | bytes | source |
|---|---|---|---|---|---|
| `Qwen/Qwen3-30B-A3B-FP8` (official) | e4m3 (OCP), block 128x128, fp32 `weight_scale_inv` | dynamic | lm_head, router (`mlp.gate`), every norm | F8_E4M3 29,896,998,912; F32 636,948,480; 7 shards, 32,449,487,768 B in files | `config.json` `quantization_config` and the safetensors API [hf] |
| `Qwen/Qwen3-30B-A3B-Instruct-2507-FP8` | same scheme | dynamic | same | F8 29,896,998,912; BF16 636,948,480 | [hf]. A different model (Instruct-2507): its golden is not today's |
| `RedHatAI/Qwen3-30B-A3B-FP8-dynamic` | e4m3, per output channel (`strategy: channel`, `observer: mse`), compressed-tensors | dynamic, per token | lm_head and every `mlp.gate` | F8 29,896,998,912; BF16 657,487,872 | `config.json` and the safetensors API [hf] |

The F8 count is exactly the four weight phases: 48 x (18,874,368 attention + 128 x 4,718,592 expert) = 29,896,998,912 [arith]. The official checkpoint stores lm_head, embedding, router and norms as F32, so the pack must convert them to bf16. That conversion is what HF does when it loads the model as bf16 (`examples/llm/prep.py:34-65` loads with `dtype=bf16`) [source].

PTPC needs no quantization run: the RedHatAI checkpoint exists. vLLM can also quantize per channel online (`VL/layers/quantization/online/fp8.py:284` dense, `:677` MoE) [source].

### 2.2 What MI300X means for the format

- gfx942 uses **e4m3fnuz**, not OCP e4m3fn: `is_fp8_ocp()` is false on gfx94x (`csrc/quantization/w8a8/fp8/common.cuh:30-42`; `vllm/platforms/rocm.py:924-933`) [source].
- vLLM converts the checkpoint at load: reinterpret the bits, map -128 (0x80, NaN in fnuz) to 0, and double the scale (`VL/layers/quantization/utils/w8a8_utils.py:110-133`; block path `fp8_utils.py:1367+`) [source]. ETX's pack must do the same, once, on the CPU.
- Dynamic activation quantization uses a maximum of 224 on fnuz, not 240 (`VL/layers/quantization/utils/quant_utils.py:27-35`; `fp8_utils.py:434-438`) [source]. W8A16 never quantizes activations, so this applies only to vLLM's baseline.
- The fnuz path does not need ROCm 6.3. Only the OCP type `__hip_fp8_e4m3` does (`csrc/quantization/w8a8/fp8/amd/quant_utils.cuh:23-40`, `:62-67`) [source].

### 2.3 Why W8A16 with per-channel weights

- **Bytes.** At batch 1 the activation is one 2048- or 768-element vector per phase. Quantizing it saves no bytes. The weights are 99.9% of the four phases' bytes [arith].
- **Inside a GEMV, per-channel is the cheap scale.** A row's dot product over K is multiplied by one scale in the epilogue. With 128x128 blocks, a row crosses K/128 scale blocks (16 for qkv and moe_up, 32 for o_proj, 6 for moe_down), so the scale enters the K loop. That adds work to a loop that is already the bottleneck (`gemv.py:25-29`) [source; arith].
- **Correctness reference.** W8A16 is exactly a bf16 model whose weights are the dequantized fp8 weights, up to summation order. The existing HF path then produces the golden, and the existing `--check-dsl` tolerance applies (section 5).
- **No wide-MFMA need.** A batch-1 GEMV is a VALU dot. The fp8 MFMA in wvSplitKQ (`__builtin_amdgcn_mfma_f32_16x16x32_fp8_fp8`, `SG:1882-2062`) needs fp8 activations, which W8A16 does not have.

The 15-30% FP8 gain in the LMSYS/AMD blog post (2026-02-11) is not evidence for this case: it is SGLang, Qwen3-235B at TP8 on MI308, with a GEMM-level claim for small, misaligned matrices and MoE gains from AITER. It is not batch 1 on one GPU.

The official block-128 checkpoint stays in the plan for one purpose: vLLM's strongest FP8 configuration may use it (section 4.2). If Stage 1 shows that the per-block scale costs nothing inside the K loop, block-128 W8A16 is an equivalent ETX recipe with the official weights.

### 3.3 What the step can become

Today's bodies (`LEVERS:36,40,43`): qkv 8.88, o_proj 5.36, moe_up 16.97, moe_down 9.89 µs per layer, 41.1 µs in total, 1.973 ms per step [source; arith]. Their achieved rates are 2.36, 3.13, 2.97 and 2.54 TB/s [arith], so none is at the stream limit.

| scenario | assumption | cut | step | tok/s |
|---|---|---|---|---|
| skeleton-bound | only the exposed VMEM halves: 37% of moe_up and 31% of moe_down (`gemv.py:26`); the same shares assumed for the dense GEMVs [unknown for them] | 0.340 ms | 4.131 ms | 242 |
| MoE at the no-stream floor | MoE bodies fall to the NOVMEM rung, 63% and 69% (`gemv.py:25`); dense bodies halve | 0.791 ms | 3.680 ms | 272 |
| all bodies halve | every byte saved is time saved | 0.986 ms | 3.485 ms | 287 |

[estimate] With the 0.19 ms of levers 1 and 2 (`LEVERS:95`), the FP8 phases still need a 0.948 ms cut: their bodies must fall to 52% of today, below the MoE no-stream floor. **On today's tile skeleton, FP8 alone does not reach 300 tok/s.** It does give the largest single gain on the list (0.34-0.99 ms against 0.19 ms).

The fp8-to-fp32 conversion adds VALU work to the same skeleton: one more instruction per 2 to 4 weights. The ablation cannot predict whether that fits under the remaining stream [unknown]. Stage 1 measures it.

## 5. Correctness gate (question 4)

### 5.1 The reference

- **Golden.** Dequantize the fp8 weights to bf16 on the CPU (fnuz conversion, then `w * scale`, rounded to bf16), write a bf16 checkpoint in a separate directory, and run the existing HF greedy path on it (`examples/llm/prep.py:34-65`). ETX W8A16 computes the same function as that bf16 model, except for the summation order. The new golden is a new file, `examples/llm/results/golden_c1024_qwen3-30b-a3b-fp8pc.txt`, with its own sha256.
- **Kernel check.** `host --check-dsl` dequantizes the weights on the host and keeps today's tolerance: 2 bf16 ulps plus a floor of scale/4096 (`examples/vllm_llm/host.hip:737-916`). Imported launches stay byte-identical (`host --check`), as now.
- **Informational, not gating:** agreement with HF's own fp8 path (`FineGrainedFP8`, W8A8 through the hub Triton kernel) and with vLLM's fp8 path. Neither is bit-identical to W8A16: both quantize activations, vLLM to fnuz with maximum 224, and vLLM computes SiLU x up in fp32 before quantizing (`fused_silu_mul_block_quant.cu:15+`). Also report the token agreement with today's bf16 golden, as model quality, not as a gate.

### 5.2 What 32/32 can and cannot show

Today's prompt is a repetitive code loop. Its smallest top-1 margin is 9.625 logits over 32 tokens [measured on the golden file]. An fp8 error large enough to matter would usually still keep 32/32, so 32/32 alone is a weak check. Add two gates for the FP8 build, written before the run:

1. **Logit gate.** Per step, the max absolute difference between ETX's and the reference's final logits, at most a bound measured on the dequantized bf16 model against HF fp32 of the same weights [unknown until Stage 2; record it before use].
2. **A second prompt** with small margins: a rotated natural-language prompt, judged with the existing tie rule (HF margin ≤ 0.5 counts as a tie, `host.hip:730`).

### 5.3 Invariants for bf16

The bf16 golden keeps sha256 `bab2f1fbe12f70179711ec40a215c74710845b73169b1cc6a3a6ca50e0a19484` [measured], and the bf16 plan keeps `434 e68e856650430532` [measured]. The import certificate fingerprints the golden file and the plan (`examples/vllm_llm/import_certificate.py:36-48`), so an FP8 build gets its own certificate and can never present the bf16 one.

## 6. Edits, file by file, and keeping bf16 alive (question 6)

The bf16 LEAD build must not change by one byte. Every FP8 piece is a new export, a new variant and a new packed directory, chosen by the model's `quantization_config`.

1. `examples/llm/model.py` `load_dims` (`:95`): refuse any `quantization_config`. This is the mandatory first edit and stands on its own. Later, accept exactly the recognised scheme and set `Dims.wdtype = "fp8_pc"`. Test: an fp8 config raises; the bf16 config's plan digest stays `434 e68e856650430532`.
2. `examples/vllm_llm/prep.py` (`:74-88`): an fp8 branch that keeps the four weight phases as fnuz bytes plus per-row scales, converts everything else to bf16, and writes to a separate packed directory with its own manifest. The bf16 branch stays as it is. Test: packing bf16 gives byte-identical files.
3. New `examples/llm/dequant_ref.py`: the CPU dequantizer of section 5.1, writing a bf16 HF checkpoint. Test: round trip on a synthetic tensor, including 0x80 → 0 and the doubled fnuz scale.
4. `etx/ops/gemv.py`: three new forms, `dsl_gemv_w8`, `dsl_moe_up_w8` and `dsl_moe_down_w8`. They take the scale pointer as one more argument. The existing forms are untouched, so their ISA and their `DSL_ABLATE_*` builds are untouched.
5. `etx/select/variants.py`: make the existing `dtype` field (`:47`, unused by legality at `:58-62`) part of legality. Every existing variant is `bf16`; the new ones are `fp8_pc`. Test: the bf16 plan is unchanged, and an fp8 plan selects only `fp8_pc` variants for the four phases.
6. `examples/vllm_llm/host.hip`: argument blocks for the `_w8` forms, and the host dequantizing reference for `--check-dsl`.
7. `examples/vllm_llm/bw_spec.py`: fp8 bytes per phase, so the timeline reports the new floor.
8. `examples/vllm_llm/build.sh`: no flag. The exports already follow the plan (`plan_exports`), so a different packed directory gives a different plan and a different certificate.
9. `examples/sessions/`: a session job per stage (section 7), committed before any GPU run, as `CLAUDE.md` section 4 requires.

Acceptance before any GPU spend: `.venv/bin/python -m pytest -q` passes; the bf16 golden and plan digests above are unchanged; `examples/vllm_llm/local_matrix.sh` builds all 16 bf16 builds unchanged; `rocm_build_check.sh` reports VGPRs and spills for the `_w8` exports.

## 8. Risks (question 7)

1. **Skeleton-bound tiles.** The MoE bodies keep 63% and 69% of their time with no stream at all (`gemv.py:25`). FP8 may give only 0.34 ms (242 tok/s). Stage 1 measures this before the full build.
2. **Register pressure.** moe_up runs at 128 VGPRs with 8 spills and fixed occupancy (`gemv.py:345-353`). The fp8 convert needs temporaries; more spills could erase the byte saving. `rocm_build_check.sh` shows the count before any GPU time.
3. **Numerics and the gate.** fnuz is not OCP: a wrong conversion (0x80, the doubled scale) silently changes every weight. 32/32 on today's prompt is too weak to catch small errors (section 5.2). Every reference (HF fp8, vLLM fp8, dequantized bf16) computes a different function.
4. **moe_down K 768.** Only 4-byte loads fit, 4 fp8 values per load. The tile may become load-instruction-bound rather than byte-bound.
5. **The baseline moves.** vLLM FP8 is also faster than vLLM bf16, if Stage 0 shows that. The comparison is then FP8 against FP8, and today's LEAD margin (-0.278 ms, `CLAUDE.md` section 1) does not carry over. vLLM's channel MoE path has no tuned MI300X config, and AITER's fp8 kernels are not checked [unknown].
6. **The claim and the model change.** The golden is no longer the bf16 model's. An fp8 lm_head, or an own quantization, changes the model further. The owner decides each.
7. **Silent bf16 packing.** Until edit 1 lands, an fp8 config is packed as raw bytes with no scales and plans as bf16 [measured]. Nothing fails loudly.

## 9. What this spec does not buy

- No measured FP8 number of any kind: every gain in section 3.3 is an estimate.
- No answer for the dense GEMVs' skeleton share: only the MoE tiles have the ablation.
- Nothing about AITER's FP8 kernels: the source is not local.
- No fp8 KV cache, no speculative decoding, no multi-token prediction.
