# DSL tile overhead, 2026-10-07

## Scope and result

This report covers the DSL tiles in `etx/ops/gemv.py` for Qwen3-30B-A3B decode at batch one on one MI300X.
The user asked for faster tiles. This is a direct user request, so CLAUDE.md section 1 permits it.
The work adds four compile flags. Each flag changes tile code only. Each flag claims bit-identical output.
No flag is on by default. The control build is unchanged.

No GPU ran for this report. All gains below are estimates.
The session file `examples/sessions/tiles.py` measures them. It also tests the bit-identity claims on the GPU.

| Flag | Change | Estimated gain, ms per token |
|---|---|---|
| `ETX_DSL_RBATCH` | The folded norm issues all its row loads before the first wait. | 0.06 to 0.17 |
| `ETX_DSL_SCALAR` | The tiles read the argument block with scalar loads. | 0.02 to 0.20 |
| `ETX_DSL_GU1` | `moe_up` streams its gate rows and up rows in one pass. | 0.04 to 0.12 |
| `ETX_DSL_WSUM` | The wave sum uses DPP and `ds_swizzle` for four of its six steps. | 0.02 to 0.12 |
| all four | The combination. The gains may not add. | 0.15 to 0.45 |

The reference is about 4.83 ms per token. A gain of 0.15 to 0.45 ms is 3% to 9% of that time.

## Starting point

These values are measurements from earlier sessions. This report does not repeat them.

1. Round11 trace: 5,081.5 us device span, 6.19 GB of known traffic, a 1,439 us floor at 4.3 TB/s. The rate is 28.3% of the floor rate. Source: `docs/qwen/BANDWIDTH-2026-10-07.md`.
2. Round37 control, the current shipped configuration: 4.832 ms device median untraced, 4.708 ms traced. Source: `results_2026-10-01/round37/FINDING.md`.
3. Round37 control trace, last decode step, mean task body over layers 1 to 47: `qkv` 11.67 us, `o_proj` 6.76 us, `router` 3.15 us, `moe_up` 18.39 us, `moe_down` 11.03 us. `lm_head` is 157.79 us once per step.
4. Layer 0 `qkv` has no folded norm. Its body is 7.78 us. The fold thus costs about 3.89 us in each of the other 47 layers.
5. Round37 ladder for `moe_up`: exposed weight loads 37%, reduction and output stores 16%, unattributed loop and flush work about 36%. The tile is skeleton-bound. It is not bandwidth-bound.
6. A coherent load that misses L2 takes about 0.50 to 0.69 us on this GPU. Sources: `hw_bench cohload` and the round11 report.

The same-binary spread of five fused runs is 0.028 ms. Round23 reports 0.017 ms. Source: `results_2026-10-01/final` and `round23/FINDING.md`.

## Diagnosis

The diagnosis comes from the ISA of the control build. The ROCm 7.2.4 container compiled it with `examples/vllm_llm/rocm_build_check.sh`.
Its megakernel uses 128 VGPRs, 8 spilled VGPRs, 36 bytes of scratch per lane, and occupancy 4. CLAUDE.md states that this report matches the VM's compiler.

### Serial round trips in the folded norm

The folded norm computes `z = bf16(sum of R rows) + residual` before the GEMV starts.
`R` is 8 for `qkv`, 1 for `router`, and 8 for `lm_head`.
In the control ISA, the loop issues the two coherent loads of one row. Then it waits with `s_waitcnt vmcnt(0)`. Then it issues the next row.
Each task thus makes `R + 1` serial round trips past L2. For `qkv`, this is 9 round trips.
At 0.35 to 0.50 us each, 9 round trips take 3.2 to 4.5 us. This agrees with the 3.89 us fold cost of item 4.

### Vector arithmetic for wave-uniform values

The DSL tiles read their argument block through a generic pointer. The compiler emits `flat_load` instructions into VGPRs.
The divergence analysis then treats every size and pointer as a different value in each lane.
Thus the stream loop computes its row and segment with a 17-instruction signed division on the VALU for each segment.
Its loop control and branches also run under exec masks.
The imported tiles do not have this problem. They read their arguments through `etx_imp_argblock` with scalar loads.

### Wave sum on the LDS pipe

The flush reduces each row partial with `etx_wave_sum`. That is six `ds_bpermute` steps.
Each step waits with `s_waitcnt lgkmcnt(0)` before the next step.
The flush is inside the stream loop. Its latency is exposed when a wave changes rows.
Round37 attributes 16% of `moe_up` and 22% of `moe_down` to the reduction and the output stores.

### Two passes in moe_up

`moe_up` computes the gate rows and the up rows as two separate stream passes.
Each pass zeroes its partials, streams, drains, flushes, and reduces across waves with two barriers.
The second pass repeats all of this fixed work. Only its weight bytes are necessary.

## Changes

All changes are in `etx/ops/gemv.py`. Each change is behind `#ifdef`. Without the flags, the emitted control source compiles to the same `mk.s` except for `hip_cuid`.

### ETX_DSL_RBATCH

The folded norm loads the residual first. Then it issues up to `DSL_RB = 8` rows before it uses the first row.
The additions keep the same operands and the same order. Thus the result is bit-identical.
For `qkv`, the expected cost changes from 9 serial round trips to about 1 or 2.
An earlier version also moved the norm weight load forward. That version spilled 23 VGPRs and added a `vmcnt(0)`. This report removed it.

### ETX_DSL_SCALAR

`dsl_args` reads every field through an `address_space(4)` pointer. The compiler then emits scalar loads.
The flag also applies `readfirstlane` to `K`, the row range, the wave index, and the block index.
The stream loop now advances its row and segment by one for each consumed vector. It no longer divides.
The weight address uses a wave-uniform base plus the lane offset. It is the same address.
The argument blocks are safe in the scalar cache. The host writes them once at setup. The step parameters go to a separate symbol, `VPS`, between launches.

### ETX_DSL_GU1

`moe_up` streams its gate rows and up rows as one pass of `2n` rows. The up rows start `ggap` elements after the gate rows.
The tile uses this path only when a test proves that no bit can change:

1. `K % 512 == 0` and `2n` fits in `DSL_RCH`.
2. With `n` rows or with `2n` rows, each row lies inside the segment range of one wave.
3. No wave range crosses from gate rows into up rows.

Under these conditions, each row is the in-order sum of one wave in both forms. The other waves add exact zeros.
Qwen3-30B-A3B meets the conditions: `n = 32`, `K = 2048`. Other shapes run the two original passes.

### ETX_DSL_WSUM

`dsl_wave_sum0` replaces the flush's wave sum. Step one uses `ds_bpermute` for the lane distance 32.
Step two uses `ds_swizzle` in xor mode for the distance 16.
Steps three to six use DPP: `row_ror:8`, `row_shl:4`, and two `quad_perm` patterns for the distances 8, 4, 2, and 1.
Only lane 0's result is used. Each step is exact on every lane that lane 0 later reads.
Lane 0 adds the same two values at each step as `etx_wave_sum` does. Floating-point addition is commutative. Thus lane 0 is bit-identical.

## Local validation

These checks ran on the local machine and in the ROCm 7.2.4 container.

1. Unit tests: 490 passed, 6 skipped. Run: `.venv/bin/python -m pytest -q`.
2. `tests/test_ops_tile_flags.py` emulates `dsl_wave_sum0` lane by lane over 2,000 random waves. Lane 0 equals the butterfly bit for bit. A negative control with a different tree differs in more than 50 of 500 trials.
3. The same file checks the `GU1` condition for `K` from 512 to 4,096 and `n` from 1 to 32. Where the condition holds, each row belongs to one wave and no wave crosses gate and up.
4. `tests/test_tile_ab.py` checks the session's verdict logic on synthetic logs.
5. Two existing audits now name the four flags: `tests/test_manifest_class.py` lists them as tile-local, and `tests/test_coherence.py` follows the weight address through `DSL_WP`.

## Predictions and thresholds

These thresholds are fixed before the session. `examples/vllm_llm/tile_ab.py` applies them.
The measure is the device median in ms per token. A gain is the flag run minus the adjacent control run.

| Flag | Basis of the estimate | Estimate, ms |
|---|---|---|
| `RBATCH` | 7 fewer round trips at 0.35 to 0.50 us in 47 `qkv` phases. 1 fewer in 48 `router` phases. | -0.06 to -0.17 |
| `SCALAR` | VALU work in the stream loop falls by 36%. The loop machinery is about 6.6 us of `moe_up`. The share on the critical path is unknown. | -0.02 to -0.20 |
| `GU1` | One drain, one cross-wave reduction, and two barriers fewer per `moe_up` task: 1 to 2.5 us in 48 layers. | -0.04 to -0.12 |
| `WSUM` | Four fewer LDS round trips per row flush. The bound is the reduction share of round37. | -0.02 to -0.12 |
| all four | The sum, less overlap between `SCALAR` and `WSUM`. | -0.15 to -0.45 |

Verdicts:

1. KEEP: the control is self-identical and the flag build is bit-identical to it. Every run is 32/32 and `CHECK-DSL OK`. All three pairs are faster. The mean gain is at or below -0.030 ms.
2. NEUTRAL: the absolute mean gain is below 0.030 ms. The flag stays off.
3. SLOWER: the mean gain is at or above +0.030 ms. The flag stays off. Record the cause from the trace.
4. REJECT: the output differs from the control, or a run is not 32/32. The flag stays off whatever its time.
5. MIXED or INCOMPLETE: no decision. Report the data as it is.

Next steps:

1. If a flag is KEEP, a later commit makes it a default. That commit updates `build.sh` and the doc for the defaults.
2. If the control is not self-identical, bit identity cannot be tested with the dumps. Then the gates are 32/32 and `CHECK-DSL` only. Report KEEP-UNVERIFIED, not KEEP.
3. If `all` is KEEP and no single flag is KEEP, keep the combination as one candidate. Report the interaction.
4. If no build is KEEP, close this item. The tile instruction overhead is then not on the critical path. The next lever is the mapping of rows to waves. See "Not done".
5. If `RBATCH` is far below its estimate, the round-trip model of the fold is wrong. Use its trace to find the fold cost before more fold work.

## GPU session

The session is `examples/sessions/tiles.py`. It needs one MI300X.

1. Setup: environment, model download, `prep`. Six builds run in parallel on the CPU: control, the four flags, and all four.
2. Correctness on GPU 0: each build runs once with `--check-dsl`. The run dumps the stage buffers after decode step 1040 with `ETX_DUMP`. It writes every step's argmax with `ETX_TOKTRACE`. The control runs twice.
3. `bitcmp` compares every dump file and the argmax file of each build with the control. It also compares the two control runs.
4. Timing on GPU 0: three rounds of adjacent control and flag runs, 30 runs in total. Round 2 reverses the order.
5. One `ETX_TRACE` run for each build. It gives the task body for each phase type.
6. Last: `rocprofv3` instruction counters for the control and for all four.
7. `verdict` prints the table of section "Predictions and thresholds".

The host exits with 0 when tokens do not match. Thus each gate job greps for `matched=32 gen=32` and `CHECK-DSL OK`.
The earlier session took 75 s per build and about 20 s per run. The estimate is 25 min of GPU time and 50 min of wall time.
At $2.99 per hour, the cost is about $2.50. Stop at 1.5 h or $4.50, whatever remains.

Commands:

```
tools/hotaisle_grab.sh 1x
tools/session.sh push <ip>
tools/session.sh start <ip> examples/sessions/tiles.py
tools/session.sh fetch <ip> results_tiles
.venv/bin/python -m examples.vllm_llm.tile_ab results_tiles
```

## Risks and limits

1. The DPP behavior of `row_shl:4` with `bound_ctrl` off is a hardware assumption. Lanes 12 to 15 of each row keep the old value 0. Lane 0 does not read them. The byte comparison tests this.
2. `GU1` adds 6 spilled VGPRs alone. With all four flags, the build spills 9. Most spill sites are in the prologue and in the reloads at task start, not in the stream loop. Their cost is not measured.
3. The VM compiler may give a different spill report. The build job prints `SPILL differs` in that case. That is a different compiler, not a failed build.
4. `rocm_build_check.sh` prints an `AttributeError` for `model_type` in every build, the control included. The DSL op list is still correct. This report did not change that script.
5. The estimates for `SCALAR` and `WSUM` assume that the removed instructions are on the critical path of the tile. Round37 shows the skeleton is on that path, but not which part.

## Not done

1. The interleaved mapping of rows to tasks for the dense GEMVs. `hw_bench stream` measured it faster on every dense shape. The model in `docs/qwen/MODEL-vllm-kernels.md` section 19 bounds it at 0.50 ms on build 3. Nobody implemented it.
   It changes the argument layout that `examples/vllm_llm/model.py` builds, not only the tile. It can also move the wave boundaries inside a row, so bit identity needs a separate proof. It is the largest open lever for these tiles.
2. Deeper load pipelines. Round34 measured `U2` against `U4` and shipped `U2` at -0.052 ms. Do not repeat it.
3. Measured losses that this work did not repeat: occupancy and waves per EU, `VL_CU=512`, batching with `NB=2`, `SPLIT_TAIL`, L2 prefetch, the top-k fold, the prep hoist, and `CU=304`.
4. `lm_head`: 157.79 us against a 145 us floor for 0.62 GB. It is near the floor.
5. The empty router tasks. `docs/qwen/LATENCY-2026-10-07.md` covers them.
