# Results, 2026-10-01: ETX reaches parity with vLLM at batch 1, and fusion finally pays

All results use one machine and one protocol on one day.
The model is Qwen3-30B-A3B bf16 with greedy decode, batch 1, and 32 generated tokens checked against HF greedy.
Every number below comes from **this** box. No row combines machines.

**Machine.** The box has 1x AMD Instinct MI300X **VF**, an SR-IOV virtual function, with ROCm 7.14, 20 cores, and 235 GB RAM.
It differs from the Hot Aisle bare-metal box used on 2026-09-30. Its compiler also differs.
The megakernel uses VGPR 128 with 15 spills here, against 9 in the ROCm 7.2.4 container.
**The earlier 4.67 ms vLLM figure comes from the other machine. Do not compare it with this page's results.**
That figure appeared before 2026-10-01.

**Configuration.** Switch set B uses `ETX_VL_XCD=1 ETX_VL_CHAIN=1 ETX_VL_DSL_GEMV=1 ETX_VL_DSL_TOPK=1
ETX_VL_DSL_ATTN=head ETX_VL_DSL_FOLD=1 ETX_VL_TOUCH=1 ETX_VL_COH=1 ETX_VL_FOLD_TOPK=0` at `ETX_VL_CU=256`.
`ETX_VL_NT` is on by default. `build.sh` includes the import prune.
The build has 60362 tasks, 436 events, megakernel LDS 29736 B, VGPR 128, and 15 spills.
Both gates pass: 32/32 tokens against HF greedy and a clean `--check-dsl` result at layer 47.

**Verdict.** ETX is **0.040 ms (0.8%) behind vLLM's best configuration**, **0.068 ms (1.4%) ahead of vLLM with
AITER**, and **fusing the tiles beats launching them one at a time by 0.200 ms (3.9%)**. The first two differences
are small but real, not noise: ETX-fused's slowest run (4.913) and vLLM-default's fastest (4.855) do not overlap in
either direction with the other's range. The fusion result is unambiguous — the two distributions are 0.19 ms apart
with a combined spread under 0.03.

**On the spreads.** The earlier ±0.003 came from three consecutive runs of one binary inside a minute.
The interleaved sequence took 15 minutes, with two container launches between consecutive ETX runs.
Its spreads are ETX fused ±0.014, ETX unfused ±0.003, vLLM default ±0.007, and vLLM AITER ±0.019.

ETX fused shows a step rather than scatter: rounds 1–3 are 4.907–4.913, and rounds 4–5 are 4.885–4.886.
vLLM default does not show that step: 4.855, 4.868, 4.867, 4.856, 4.869.
Thus, the change is not box-wide drift. Its cause is unknown.
The verdict remains unchanged. ETX's best round, 4.885, exceeds vLLM's worst, 4.869.

## What moved the number, each measured on this box

| change | before | after | delta | what it is |
|---|---|---|---|---|
| `ETX_VL_COH` | 5.224 | 4.907 | **−0.317** | DSL tiles access activations coherently (sc0 sc1) and skip the per-task `buffer_inv sc1` acquire, which had been invalidating the XCD's whole L2 at every phase boundary |
| `ETX_VL_FOLD_TOPK=0` | 5.291 | 5.060 | **−0.231** | stop folding the MoE top-k into every expert task |
| `ETX_VL_NT` | 5.021–5.034 | 4.911–4.916 | **−0.106** | non-temporal weight loads, so weights read once per token stop evicting the MALL-resident KV cache |
| `ETX_VL_CU=256` | 5.327 | 5.260 | **−0.067** | 256 tasks per dense phase instead of 304 |
| import prune | 5.026 | 5.010–5.012 | **−0.015** | `build.sh` imported `wvsplitk` even when `ETX_VL_DSL_GEMV` replaced it, and its 32768 B declaration sized the LDS arena |

The COH row uses an A/B from the same binary generation at the end of the day.
With `ETX_VL_COH=0`, three runs give 5.224/5.223/5.227 and match 32/32 tokens each.
COH off also produces a smaller build: 11 spills against 15.
Each table row uses its own build generation, so intermediate baselines differ slightly. Do not add the row deltas.

**The top-k fold cost more than all the additions that day.**
Under `ETX_VL_DSL_FOLD`, 448 expert tasks per layer each recomputed the same 128-logit softmax and top-8 selection.
There were 192 `moe_up` tasks and 256 `moe_down` tasks.
Wave 0 did this work while the other fifteen waves waited at the barrier.

A timing-only ablation with fixed expert ids measured **0.676 ms/token**.
The revised design keeps norms folded and restores one top-k launch per layer.
That extra phase and handoff still save 0.231 ms.

## Measured and rejected

Each was built and run. Each number is against its own control on this box. All are off by default and the numbers
are recorded in-source so they are not retried blind.

| idea | result | why |
|---|---|---|
| `ETX_VL_ARGPF` — prefetch the next task's argument block during the arrive | −0.003 (neutral) | inside the spread<br> emission complexity for nothing |
| `ETX_VL_BAR2` — 3 barriers per task down to 2 | **+0.095** | after the fix that moved its global load off the publication path<br> it raises megakernel LDS 41448 → 61952, and one barrier is worth ~0.02 ms |
| 16 B split-tail so `moe_down` (K=768) leaves the 8 B load path | **+0.144** | per-load address tracking and a second per-row wave reduction cost more than the wider loads save<br> `moe_down` body 12.01 → 14.71 µs/layer |
| `ETX_VL_ATTN_WIDE` — attention block across 8 XCDs instead of 4 | +0.008 | the block is latency-bound, not parallelism-bound: `prep` moves 2.5 KB per task in a 5.9 µs body, 1.5% of one workgroup's streaming rate |
| batching `topk`'s coherent stores | +0.008 | its body is one write-through round trip that all stores sit behind, not 24 separable costs |
| dropping `topk`'s unused `tei` output | −0.004 | inside the spread<br> not worth diverging from vLLM's signature |
| skinny GEMM, dense phases only, B=2 | **+0.293** (7.104 batched vs 6.811 replicated) | the shared weight read buys 7%, because the second column doubles LDS reads and FMAs<br> and a batched phase must wait on every request's previous event, so it loses the slack replication provides |
| smaller workgroups for occupancy | not built | waves/SIMD = min(512/VGPR, LDS-limited)<br> at 128 VGPRs the VGPR term is 4 regardless of workgroup size |
| fusing `prep` into `attn` | not built | `prep` is in-place and non-idempotent — it norms and ropes qkv rows back into themselves, so any shape with more than one task per kv head is *wrong*, not merely slow |
| sweeping `PART` for attention partitions | not built | `parts = ceil(MAXLEN/PART)`<br> 256 is the minimum correct value, 512 leaves tokens 768+ unattended, 128 only adds early-exiting tasks |
| `ETX_DEV_RESET` — the kernel rewrites its own per-step state so the host enqueues nothing | −0.008 wall (0.16%) | the host's 40.8 µs of enqueues do disappear (reset/step 57.8 → 17.0 µs) but 14 µs returns as device time — one workgroup copies the init images while the other 303 have exited — and the rest is absorbed by the wait<br> correct and available, not worth its machinery in the default build |

## Occupancy and cache, measured with rocprofv3

Counters filtered to `etx_megakernel_d0` — the run also issues 12,807 rocclr copy/fill dispatches that ruin any
unfiltered average. `rocprofv3` SIGSEGVs at teardown *after* writing its database, so the data is intact.

- **Occupancy is 4.000 of 8 waves/SIMD** (`MeanOccupancyPerActiveCU`, min = max across all 1055 dispatches), with
  98.6% of CUs occupied. Both resources bind at once: VGPR 512/128 = 4, LDS 65536/41448 = 1 workgroup. After the
  import prune LDS would allow 2 workgroups per CU, but VGPR still caps at 4. Reaching 6 waves/SIMD needs VGPR ≤ 85
  **and** LDS ≤ 21845 B; 8 needs ≤ 64 and ≤ 32768 B. `-DETX_MIN_WG_PER_CU=2` reaches the emitted
  `__launch_bounds__(1024, 2)` and the allocator still produces 128 VGPRs; `-mllvm -amdgpu-waves-per-eu` does not
  exist in ROCm 7.14's clang.
- **The fused kernel is not penalised here.** `etx_unfused_d0` is VGPR 104 → 512/104 = 4 waves/SIMD, the same. The
  hypothesis that a megakernel's max-over-all-tiles budget caps occupancy where separate launches would not is
  **refuted for this model**: both are register-capped at the same level.
- **85.9% of wave-cycles are `SQ_WAIT_ANY`** (303.8 M of 353.8 M) while `MemUnitStalled` = 0.0 and
  `LdsBankConflict` = 0.3. Waiting with the memory pipe never backing up means too little memory-level parallelism,
  not too little bandwidth — the same conclusion as the occupancy cap, from the other side.
- **L2 hit rate 31.9%** (`TCC_HIT` 23.84 M vs `TCC_MISS` 50.93 M), and 99.9% of misses become fabric reads at
  119.5 B per request for 6.08 GB — no read amplification. With `ETX_VL_NT` the hit rate rises to **34.6%** and DRAM
  read requests fall 3.9% (50.87 M → 48.91 M), worth the measured 0.106 ms.
- **Instruction cache 99.90%** (`SQC_ICACHE` 6,815,943 hits, 6,958 misses). The megakernel's switch over ~400 task
  types does not thrash it, contrary to the concern ForgeMegakernel raises in the literature. Ruled out.

## A third class of bug: the emitter and the compile disagreeing

Twice today, a feature reached the final `hipcc` through a `-D` flag, but the emitter made its decision independently.
The two stages disagreed without a diagnostic.
`ETX_VL_NB` for skinny GEMM would have made extra requests read column 0.
`ETX_DEV_RESET` had a worse defect.
`build.sh` appended the flag to an array, then **overwrote that array** whenever `ETX_VL_COH` was also set:

```sh
COHF=(); [ "$ETX_DEV_RESET" = 1 ] && COHF+=(-DETX_DEV_RESET)
if [ "$ETX_VL_COH" = 1 ]; then COHF=(-DETX_DSL_COH); fi   # drops it
```

— which is every build of the best configuration. The host believed in a reset tail that was never compiled, skipped
its own reset, and every step after the first became a no-op: all workers surplus, 0/32 tokens, no error. (The
earlier diagnosis that the define "reached the final hipcc but not the device-code compile" was wrong; it reached
neither.)

The fix changes the feature contract.
A conditional device feature that the host must know now lives in `plan.graph.codegen`.
`emit_plan_header` publishes it as `ETX_EMIT_<FEATURE>` in `plan_data.h`.
The host uses that definition. Its environment variable can only turn **off** an emitted feature.

The build compiles the kernel and host together, and both include that header.
A disagreement would require the emitter to contradict itself within one call.
`tests/test_feature_manifest.py` checks both directions for `argpf`, `bar2`, and `dev_reset`, with a marker unique to each feature.
The build passes no `-D` for these features.

The same round corrected the event-order argument in `etx_device_reset`.
The exit counter and per-task arrives use relaxed atomics on different addresses.
The counter can reach `gridDim.x` without an order guarantee for the arrives.
A late arrive could decrement an event word after reset, which could cause a hang after an unbounded number of correct steps.
A release fence before the increment and an acquire fence after the full count close the race.

## Two methodology errors caught today

**The traces covered the prompt, not decode.**
`--max-steps 8` stops inside the teacher-forced prompt, where `seq_len ≤ 8`.
vLLM's paged-attention kernel partitions by a hardcoded 256 tokens and returns immediately past the sequence end.
See `vllm/csrc/rocm/attention.cu:362,366-369`.
Thus, 16 of 20 `attn` tasks looked trivial, and the phase looked 4.3× imbalanced.

During decode, all 20 bodies take 5.7–6.7 µs, a 1.17× spread.
The `attn` body is 6.28 µs, not 1.91.
**This did not affect timing.** `host.hip:512` records only steps at or after the prompt end.
But three rounds of phase analysis used those traces, including a nonexistent “partition imbalance worth 0.17 ms”.
The weight-stream phases do not change: `qkv` is 6.62 vs 6.66, and `moe_up` is 20.03 vs 20.03.

**`span − mean body` attributed work imbalance to skew.**
A phase ends when its last task finishes.
Thus, `span = (that task's start delay) + (that task's body)`.
Subtraction of the mean body misattributes the difference between the critical and average task to start delay.

This method inflated `router`'s apparent skew to 4.34 µs/layer. Its actual start delay is 0.68.
At `CU=256`, 97 of its 256 tasks are empty, which halves the mean.
`docs/qwen/BUDGET-2026-10-01.md` gives the corrected split.

ETX's orchestration is no longer the limiting factor: the handoff is at the protocol floor, the start delay is below
the hardware's own dispatch jitter, and fusion wins by 0.200 ms. What remains is dominated by the quality of the DSL
tiles, which is a larger item than the entire 0.040 ms gap to vLLM.

## Batch

ETX replicates rather than batches: `ETX_VL_REQUESTS=N` instantiates N copies of the task graph (60362 / 120724 /
239912 tasks and 436 / 872 / 1552 events for N = 1/2/4), so every request streams its own copy of the weights, while
vLLM reads a weight tile once per B-column activation matrix. Measured on this box, ETX/vLLM per token is 1.08× at
B=1, 1.29× at B=2, 1.90× at B=4. Batch is currently ETX's worst regime. The skinny-GEMM experiment above shows why
batching the dense phases alone does not fix it: the shared weight read is only 7% of the dense body, and the join
costs more than it saves. Closing this needs the whole layer to batch, MoE included, and a matrix-instruction dot
product for B > 1 rather than more scalar FMAs.
