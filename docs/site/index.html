Design note · v0.3 · 2026-09-22

ETX：一个 DSL 无关、chiplet 感知的动态 Megakernel 编译器

把「多个 GPU 算子融合进一个持久化内核，同时处理动态 shape 与数据依赖」做成一个编译器，而不是一份手写内核。抽象沿用 Event Tensor（MLSys 2026），再补上论文没有的两样东西：显式的机器模型，和按代价选出来的调度策略。

依据 arXiv 2604.13327 v2（Event Tensor / ETC，CMU + NVIDIA） 参照 MPK、Hazy no-bubbles、fleet-mi300x（MI300X 上的手写 megakernel） 状态 设计稿，未实现
01 · 论文拆解

ETC 到底做了什么

论文的核心是一个 IR 级别的抽象，不是一个新调度器。它把 megakernel 里「谁等谁」这件事，从散落在手写内核里的信号量，提升成编译器里的一等张量。剩下的静态 / 动态调度，都是对这个张量做变换。

1.1 三个语言构件

device function

任务网格

一个函数，按多维坐标启动成一组 tile 级任务。每个任务在一个 SM 上跑，内部可以 warp 特化、用 tensor core。任务坐标是符号表达式，比如 (n, 4)。

Event Tensor

事件张量

多维数组，每个元素是一个事件：初始等待计数 wait_count，支持 notify()（原子减一）、wait()（自旋到零）。动态调度下事件归零还能触发消费者任务。shape 可以含符号维度。

graph function

图函数

由 call_device 组成的计算图，节点既有数据张量也有事件张量。每次调用用 in_edges / out_edges 加一个 einsum 风格映射（如 "ij->i"）声明 task 坐标到 event 坐标的关系。

1.2 两种动态性怎么进 IR

shape 动态
Tensor 与 ETensor 的维度都可以是符号变量（batch、seq len）。编译产物是一个模板，运行时填具体值就得到当次的任务图，不重编译、不重新捕获 graph。这是它能 AOT 的根本原因。
数据依赖动态
两个机制。数据依赖更新：谁通知哪个事件由运行时张量决定，如 "i->topk[i,:]"（token i 通知它被路由到的 k 个 expert 事件），并且事件的初始计数也在算 topk 的那个 tile 里一起算出来。数据依赖触发：一个事件触发多少消费者由运行时决定，如 "i->range(indptr[i], indptr[i+1])"（expert i 触发它需要的 GroupGEMM tile 数）。
不变量
整条依赖链仍然是前馈的：Attention → TopK → 分组 → GroupGEMM。动态只出现在后段的通知目标和触发范围上，图本身没有环、没有任意控制流。

1.3 两条调度变换

维度静态调度（§3.1）动态调度（§3.2）
谁决定任务顺序host 在启动前为每个 SM 排好队列（论文用 round-robin），物化进全局内存片上调度器：事件归零时把消费者任务原子 push 进就绪队列，空闲 SM 原子 pop
依赖如何保证消费者任务开头 wait()，生产者任务结尾 notify()同样的 notify / wait，外加 push / pop

02 · 批判性阅读

从论文读出的七个架构判断

  1. 事件就是整型计数器，这个决定要保留。它让运行时状态压缩到两块内存，让符号 shape 的编译器基础设施能直接复用。任何「事件对象」「任务图节点」都是退步。
  2. 调度是编译器变换，不是运行时组件。static / dynamic 都是对同一个 IR 的改写，运行时只剩 push / pop 两个函数。这使得策略可以按子图组合，而不是全局二选一。ETX 的 hybrid 调度就是在这个基础上做的。
  3. 机器模型是隐式的，而且只在 B200 上成立。论文假设 SM 均质、L2 统一相干、有 multimem 归约写、有 NVLink。一张 MI300X 至少四处不成立：L2 是 8 段各 4 MB 的 XCD 私有缓存；没有 multimem；跨 XCD 原子走 Infinity Fabric；系统域原子对内存类型有要求。论文说抽象「不针对特定 GPU 代际」，是对 IR 说的，实现没验证过。
  4. 静态调度对动态性的兜底太粗。shape 用「下一个更大的采样值」的队列；数据依赖直接退化成 E[0] 全局屏障。这在 MoE + 低 batch + 跨卡这种最常见的组合上正好是最差的一档，需要 hybrid 补上。
  5. 动态调度的代价是拓扑函数。TP=4 上 0.83× 说明 push 一旦跨设备就得不偿失；中心化全局队列作者也承认有争用。队列必须分层，push 必须有域界。
  6. tile 质量与融合收益必须解耦。作者承认生成的 GEMM tile 在某些配置下不如 cuBLAS，导致 TP=4 上偶尔落后。系统必须允许内联手写 tile（CUTLASS / CK 风格），并且评测时把「融合的收益」和「tile 的质量」分开报。
  7. 每步一次启动，图内没有循环。论文的 megakernel 覆盖一次解码迭代，continuous batching 的形状变化靠符号 shape 吸收，但内核本身每步重启。跨步持久化（内核常驻、host 通过环形缓冲喂步描述）论文没做，这是延迟敏感场景下另一个可拿的量。
  8. 只有任务级的依赖变换，没有「改图」的变换。ETC 能把一个算子拆成 tile 并细化依赖，但不会删相位：没有以重算换事件、没有跨屏障的权重预取。小 batch 下关键路径由相位数和每相位固定延迟决定，这两项正是手写内核（Hazy、fleet-mi300x）和它拉开差距的地方。第 05 节把这笔账算清楚。

从 fleet-mi300x 带来的经验

我们在 MI300X 上手写过同类 megakernel（DeepSeek-V2-Lite bs=1 解码，3.60 ms/token，比同机 vLLM 快 20%）。那份工作证明了三件事：跨 XCD 事件与 XCD 内事件的代价差一个量级，一层 MoE 里能把全局事件从 10 压到 3、XCD 局部事件 24 个；生产者 buffer_wbl2 回写不能省，消费者 L1 失效不能省；持久化内核的 workgroup 到 XCD 映射不是契约，要在启动时探测。这三条都直接进了 L3 与 L5 的设计。

03 · 定位

ETX：目标、非目标、三个硬决定

ETX（Event Tensor eXtended）是一个位于 tile DSL 之上的编译器：它不生成 tile 内的指令，只负责切 tile、连依赖、排调度、放置到机器上、生成持久化内核的骨架，再把各家 DSL 编译出的 tile 体链接进去。

目标 · 按优先级
  1. DSL 无关：Triton、TileLang、CuTe DSL、CK、手写 HIP / CUDA 都能接。
  2. 硬件可移植：同一份 IR 在 CDNA2 / CDNA3 / CDNA4、RDNA、NVIDIA Hopper / Blackwell 上都出正确且合理的代码，chiplet 是一等概念。
  3. 动态负载一等支持：shape 动态、数据依赖动态、跨步动态（continuous batching、speculative decoding）。
  4. 调度决策自动化且可解释：编译器按代价表选 static / dynamic / hybrid，并打印理由。
  5. 可验证：每个融合内核都有可逐元素比对的未融合参考，死锁能定位。
非目标 · 明确不做
  • 不做训练框架；第一版只做推理侧融合。
  • 不自研全部 tile 级代码生成；允许内联已调优的手写 tile。
  • 第一版不做跨节点；IR 不写死单机，调度器先只看单机拓扑。
  • 不追求所有算子都能融合；融合失败要优雅退化成部分子图融合 + 逐内核执行。
  • 不处理任意控制流；依赖必须能写成仿射映射或运行时范围映射。

三个硬决定

决定内容违反的代价
硬件差异只以数据存在pass 里不许出现 if arch == gfx942。所有差异写在 arch/*.yaml 的能力表、代价表和 lowering 表里。新硬件接入要改 pass，每个 pass 都变成 if 森林
能力与代价分开建模capability 是布尔 / 枚举，决定「能不能做」，错了是错的代码；cost 是数值，决定「值不值得做」，错了只是慢。混在一起后没法回答「这个优化在这台机器上是不支持还是不划算」
调度策略由代价模型选每个子图独立决策 static / dynamic / hybrid，输入是负载特征 + 拓扑代价，输出附带理由。论文 TP=4 上 0.83× 的重演

再加一条贯穿全部层的纪律：依赖语义、机器事实、放置决策三条线永不混写。依赖错了结果错或死锁，放在 L2；机器事实错了是静默错或性能差，放在 L3；决策错了只是慢，放在 L4。每条线出问题都能只查一层。

05 · 性能模型

两个下界与四个杠杆

在写任何 pass 之前先把账算清楚：megakernel 到底能从哪里拿时间。解码一步的时间有两个下界，取大者：

T_step ≥ max( Σ bytes / BW_HBM ,                                   # 带宽项
              Σ_相位 ( bytes_相位 / BW_HBM + T_fixed(相位) ) )       # 关键路径项
T_fixed(相位) = 信号延迟 + 排空（最慢 worker 与平均的差）+ 下一相位的 prologue 爬坡

大 batch 时带宽项占优，融合能拿的是相位边缘的空洞（wave 量化、启动间隙），收益 5% 到 15%。小 batch 时关键路径项占优，这时 megakernel 不是「重叠」而是「把链弄短」。同一套技术在两种场景下的倍数差一个量级，原因全在基线离下界多远：

3 · 跨屏障重叠等事件的空转权重不依赖任何事件：worker 在自旋时把下一相位自己那份权重流进 LDS / 寄存器，事件一到直接算（Hazy 到 78% MBU 的主要办法）L4 Pass 7 + LDS 分页 + 资源类固定延迟被下一相位的字节填满
4 · 细粒度事件排空（等最慢的 worker）全局事件拆成按 head / 按行的事件（论文的 ij->i），消费者只等自己的生产者，straggler 只拖累自己的下游L2 边映射 + Pass 2 分片真全量的依赖点仍要等全部

合起来，一层的时间从「7 × (字节/带宽 + 固定)」变成「3 × 字节/带宽 + 3 × 被预取填掉的固定延迟」，才有机会贴近 31 µs 的带宽项。这四个杠杆里，ETC 只有第 4 个；MPK 和 Fleet 有 2 的一部分；Hazy 手写了 1、2、3。ETX 把四个都做成 pass，这是它对手写内核的追赶路线，也是它对 ETC 的主要增量。

对收益的诚实预期

30B 以上 dense 模型、bs ≥ 16：对 vLLM / SGLang 10% 到 30%，上限由基线 MBU 决定。MoE 小 batch 与 TP：基线 MBU 只有 10% 到 25%，1.5× 到 3× 是有物理空间的，但要同时拿到杠杆 1 到 3，只把算子塞进一个内核拿不到。评测一律报 MBU 和每相位的 trace，不单报倍数。

Tile 契约：DSL 无关怎么落地

megakernel 编译器只做三件事：切 tile、连依赖、排调度。三件事各需要一份输入。所以任何前端只要能回答三个问题，就能接入；答不出来的，就不该硬接，而应退化到逐内核执行。

5.1 两种接入模式（这是 DSL 无关的真正机制）

「DSL 无关」不能只是一句 IR 层的声明。tile 体最终要和持久化循环编到同一个内核里，不同 DSL 能给出的产物形态不同，所以后端要提供两条路：

link 模式

tile 体是可链接的设备函数

前端把每个 tile 体编成一个符合固定 ABI 的设备函数（-fgpu-rdc / -rdc=true），ETX 用 HIP / CUDA C++ 生成持久化循环与 dispatch switch，链接时合并。CUTLASS、CK、CuTe DSL（导出 device function）、手写内核走这条路。

优点tile 体不用知道 ETX 存在；可以内联厂商库级别的 tile。
代价跨翻译单元内联受限，寄存器分配按全内核取并集。

host-DSL 模式

持久化循环用 tile 的 DSL 生成

Triton 不导出可链接的设备函数，但 @triton.jit 函数可以互相调用。ETX 为这类前端生成一个同 DSL 的持久化内核：循环、pop、wait、dispatch 都用该 DSL 写，运行时原语通过 tl.atomic_*、extern 库函数或 inline_asm 提供（Triton-Distributed 已证明这条路可行）。

优点整内核在一个编译单元里，能整体优化。
代价每支持一个 DSL 要写一个骨架模板；DSL 的表达力限制骨架（比如 Triton 没有 warp 特化）。

Event Tensor IR

6.1 核心类型

Tensor  = (shape[sym|const], dtype, layout_hint)

wait_count
归零前需要的 notify 次数。可以是常量、符号（WORLD_SIZE），或运行时值（路由到 expert i 的 token 数），运行时值必须由某个上游 tile 写出。

事件的可见性范围：workgroup < cluster < domain < device < system。domain 是 ETX 相对论文新增的一级，对应 XCD / GCD / die。论文的事件只有一种 scope（device），这在均质 L2 上没问题，在 chiplet 上是一个量级的代价差。
domain_id
这个事件主要服务哪个 exec domain 的任务。由 L4 的分片 pass 填，L2 里留空。
init_kind
static（常量）、per_step（host 每步写入，如 batch 相关计数）、runtime（某个 tile 写入，如 MoE 路由计数）。

6.2 边映射的四种形式

形式例子用途编译期能分析什么
仿射（einsum 子集）"ij->i"规约、拆分、静态依赖精确扇入扇出，可静态排队
索引算术"ij->(i/2)j"tile 尺寸不匹配（RS tile 是 MM tile 两倍）同上
运行时范围"i->range(indptr[i], indptr[i+1])"一个 producer 触发变数量消费者（MoE expert → GroupGEMM tile）只知道上界；静态调度只能按上界排队并用 wait_count 兜底

约束是分析能力的前提：映射必须是仿射的，或 range(仿射, 仿射)、gather(张量) 形式；禁止任意控制流进边映射；运行时值张量必须来自上游 tile 的写出，且带 release 语义。

6.3 语义（这是 IR 的一部分，不是后端细节）

arrive(ev)  ≡  release-fence; atomic_dec(ev.count)       → 结果为 0 时 ev 触发
wait(ev)    ≡  spin_until(ev.count == 0); acquire-fence
trigger(ev) ≡  arrive 返回 0 时，把 ev 的消费者任务集合 push 进调度器（仅动态 / hybrid）

生产者的写必须在 arrive 之前对消费者可见（release），消费者的读必须在 wait 返回之后（acquire），而且是在事件的 scope 上成立。后端若发现目标硬件在该 scope 上无法提供这个语义（见 L3 的原子陷阱），必须编译报错，不许静默降级。

6.4 校验 pass（必须全绿才允许进 L4）

校验检查不做的后果
无环任务级依赖图无环（符号维度取任意值都成立）死锁，现场极难定位
计数守恒wait_count 等于实际扇入（运行时范围取上界，且初始化 tile 必须在图中）早触发（结果错）或永不触发（死锁）
运行时值先行indptr / topk 类张量的写出 tile 在依赖图上严格早于所有读它的 arrive / trigger读到旧路由，MoE 结果错但看起来正常
tile 覆盖唯一每个输出元素恰好被一个 tile 写静默数据竞争
scope 单调跨 domain 的边所用事件 scope ≥ domain；跨设备 ≥ system本地可见、远端看不见
协同驻留可满足持久化内核的 worker 数 ≤ 目标的共驻上限（按资源类算）worker 不共驻 → 等一个永远不会被调度的生产者

三个静默错误陷阱（AMD 原子）

1. coarse-grained 内存上的 system-scope 原子会被降级为 device scope。跨卡事件张量必须用 fine-grained 分配。
2. PCIe 不支持某原子时，GPU 侧退化成 load-op-store，CPU 看到的不是原子序列。
3. MI200 的浮点原子不能过 Infinity Fabric，在 uncached 内存上可能直接 NOP。
结论：事件张量的分配器是 L4 的一部分，按 scope 选内存类型，并在编译期断言合法组合。这一条是我们把 scope 放进 IR 的直接原因。

09 · L4

放置与调度 pass

七个 pass 按顺序跑，每个 pass 只读 L3 的表，输出都是数据，不改 IR 语义。

Pass 1 · tile 尺寸与资源类

输入 TileOp 的抽象资源需求与目标容量，输出每个算子的 tile 尺寸与 tile 数。64 KB 与 160 KB 的 LDS 会改变可行 tile 尺寸，所以同一算子在 gfx942 和 gfx950 上 tile 数不同，事件张量的 shape 随之变，这正是 shape 保持符号的好处。

这一步还要解决论文没提的寄存器并集问题：一个内核的 VGPR / LDS 占用取所有 tile 类型的最大值，最重的 tile 决定全内核的占用率。ETX 把 tile 按资源分成资源类；同一资源类的 tile 进同一个持久化内核实例。多个实例同时驻留（不同流、各占一部分 CU），共享同一张事件张量。这个「内核族」机制和多设备实例是同一套代码（见 L5）。在 fleet-mi300x 上我们测过 343 个寄存器的并集对带宽受限的 GEMV 没有损失，所以资源类是一个可选优化，不是必需项；代价模型决定要不要拆。

LDS 同理不按最坏情况分配，而是切成固定大小的页（Hazy 在 H100 上是 13 页 × 16 KB）。tile 体向页分配器申请和释放，下一个 tile 的权重装载可以在当前 tile 还在写回时开始。页数由资源类和 L3 的 lds_kb 算出：gfx942 4 页、gfx950 10 页、sm_90 13 页。

Pass 2 · 事件亲和性分片（chiplet 感知的核心）

问题形式：把任务 / 事件图切成 k 块（k = domain 数），最小化跨块边权之和，边权 = 扇入扇出数 × 该边的 T_sync。第一版用贪心加局部改进：

  1. 以扇入扇出最大的算子为种子，把它和它的事件放进同一 domain（MoE 的 GroupGEMM 与 expert 事件；attention 的 head 与它的 merge）。
  2. 连续 tile 坐标落同一 domain，再叠 GROUP_SIZE_M 式 swizzle 保 L2 局部性。
  3. 跨 domain 边超预算时，把该事件提升到共享缓存作汇聚点，或把这条边改成静态长队列（不 push）。

输出：每个任务的 domain_id、每个事件的 scope 与存储类型（普通 VRAM / 共享缓存常驻 / 跨卡 fine-grained）。fleet-mi300x 的一层 MoE 里，这一步和 Pass 3 一起把全局事件从 10 压到 3，其余 24 个都是 XCD 局部的。

Pass 3 · 事件消除：以重算换同步（杠杆 1）

一个事件存在，是因为某个生产者的输出要被很多消费者用。如果生产者是纯函数、它的输入已经被更早的事件同步过、而且它便宜，那就让每个消费者在自己的 prologue 里重算它，事件和生产者任务一起删。付出的是并行的冗余微秒，换回的是串行的同步微秒。

Pass 4 · 调度模式选择

S_balance = 动态调度预计省下的 straggler 时间（由负载方差估计或历史 profile）
C_cross   = 跨 domain push 次数 × T_cross（跨设备则 × T_dev）
C_queue   = 队列争用代价（标定曲线，随竞争者数上升）

选 dynamic   当 S_balance > C_cross + C_queue 且无跨设备边
选 hybrid    当 domain 内有不规则负载、domain 间边多
否则 static

决策必须可解释，编译日志形如：

subgraph moe.group_gemm : hybrid   (S_balance=+7.6%, intra-domain dynamic, 3 cross-domain edges → static)
subgraph attn.qkv_rope  : static   (S_balance≈0, 0 cross-domain edges)
subgraph tp.gemm_rs     : static   (cross-device edges=18, C_cross=2.1ms > S_balance=0.4ms)

Pass 6 · 内存规划与事件分配

  • 中间张量的生命周期与放置：domain 内消费的中间量优先放能被该 domain 的 L2 抓住的位置（fleet-mi300x：每层 1.2 MB 的压缩 KV 缓存整层留在 XCD 的 4 MB L2 里）。
  • 事件张量按 scope 选内存类型（普通 / uncached / fine-grained），编译期断言与 L3 的 visibility 表一致。
  • 静态路径把每个 worker 的预排队列物化到全局内存；描述符压成定长记录 (subgraph_id, coord, task_type)，不做指针追逐。

Pass 7 · 跨屏障权重预取（杠杆 3）

屏障挡住的是激活值。权重不依赖任何事件，静态可知，所以 worker 在自旋等事件的那段时间可以已经把下一相位自己那份权重流进 LDS 或寄存器，事件一到直接算。效果是每个屏障的固定延迟被下一相位的字节填满。

不重叠：  [phase k 算][等事件 · 空转        ][phase k+1 读权重][算]
重叠：    [phase k 算][等事件 · 同时读 k+1 权重][算]

这个 pass 做三件事：

  1. 静态段的下一任务可知：worker 的预排表里下一个任务是确定的，编译器把它的权重切片地址算进当前任务的 epilogue；动态段用 early push 之后也能知道，只是晚一些。
  2. 落点由能力表决定：gfx942 没有 TMA，直接到 LDS 只有 32 bit / lane，预取进 VGPR / AGPR 或只做 L2 预热；gfx950 有 128 bit / lane 的直接到 LDS；Hopper / Blackwell 走 TMA 加 mbarrier。这是「能力决定做法」的典型例子，不能写成一段通用代码。
  3. 与资源类、LDS 分页一起决策：预取占寄存器和 LDS 页，会挤掉当前 tile 的占用。fleet-mi300x 单独加过一版 --prefetch-next，慢 4%，原因是寄存器压力和 L2 污染；Hazy 之所以能到 78% MBU，是分页和预取一起设计的。所以 Pass 1 的资源类要把「预取缓冲」算作 tile 的资源需求，代价模型按 T_fixed(屏障) − 预取造成的占用损失 决定开关。

预取和 Pass 3 是互补的：Pass 3 删掉能删的屏障，Pass 7 把删不掉的屏障的等待时间用掉。

9.3 内核族：一个抽象覆盖多设备与多资源类

一次 Step 可以由多个内核实例执行，每个实例是一个 (device, resource_class) 对，共享同一张事件张量（同设备用普通 / uncached 内存，跨设备用 fine-grained）。三种场景是同一条路：

  • MI250X：两个 GCD 是两个设备，一张卡启动两个实例，跨 GCD 事件是 system scope。
  • 8 卡 TP：八个实例，跨卡事件 system scope，通信 tile 内联在各自实例里。
  • 寄存器并集拆分：同一设备两个资源类（重 GEMM / 轻 GEMV），两个实例各占一部分 CU，事件 device scope。

调度器不知道实例，只知道 domain 树；实例只是树的一棵子树被交给了一个内核。

10.4 通信融合在没有 multimem 时怎么办

论文 1.40× 的 GEMM + Reduce-Scatter 建立在 multimem.ld_reduce（NVLink SHARP）上，CDNA 没有对应指令。候选路径三条，都要单独实验，做不出正收益就在能力表里写 comm_fusion.reduce_scatter: unsupported，只做计算侧融合：

  1. owner 侧归约：每个 rank 的 GEMM tile 把结果写到 owner rank 的 fine-grained 缓冲区，owner 的 RS tile 等事件后在本地 L2 归约。写是单向 P2P store，事件是跨卡 arrive。
  2. P2P 浮点原子累加：MI300 支持浮点原子过 IF，MI200 不支持；精度上求和顺序不确定，需要 fp32 累加加一次 bf16 舍入。
  3. 借用 rocSHMEM / Iris 的一侧通信原语作为 tile 体，把 ETX 只当调度器用。

13 · 验证

验证策略

正确性
  • 协议模拟器：host 上用 Python 模拟事件协议，对采样 shape 与随机路由跑整个任务图，检查无死锁、计数守恒、每个 tile 的输入在它执行前已被写。fleet-mi300x 已有原型（3 个 token 的事件协议模拟 + 12 个注入缺陷的变异测试）。
  • 差分测试：每个融合内核配一份未融合参考（逐算子提交、同 tile 代码 + 全局屏障），随机 shape、随机路由，逐元素比对。
  • scope 测试：专门构造跨 XCD / 跨卡的事件，验证真的可见；能抓住系统域原子被静默降级。
  • 原子能力断言：对目标内存类型做一次原子写读回，不成立则编译期失败。
  • 看门狗：所有测试带超时，hang 视为失败，并 dump 事件张量（哪个事件计数没归零、谁没 arrive）。
性能
  • 基线三档分开报：逐算子提交、同 tile 代码 + 全局屏障（隔离出「融合收益」）、官方库（cuBLAS / RCCL、CK / hipBLASLt）。
  • 每个 PR 跑固定 shape 集合，超阈值报警；报数一律带 shape、batch、并行度。
  • 调度决策日志入库，事后能回答「为什么这个子图选了 static」。
可移植性回归
  • 同一份 IR 在 gfx90a / gfx942 / gfx950 / sm_90 上跑同一个小模型：逐元素一致、不 hang。
  • 决策日志必须打印能力位差异，证明决策真的读了机器模型，而不是碰巧一样。
  • 能力表里每个 discover 字段（如 XCD 映射）在 CI 里跑探测并与 yaml 对账。
